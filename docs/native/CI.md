# Native CI

The workflow is `.github/workflows/native.yml` ("Native CI"). It never uses game data: the runner is built and started without a game, and the tests use synthetic data. The existing `ci.yml` (pytest and the game-data guard on every PR) stays as it is.

## Triggers

| Trigger | What runs |
|---|---|
| `push` to `native` or to a `wp/**` branch | `tools`; `native`, `native-tsan`, `native-windows`, `native-macos`; `changes`, then `runner` if it says so |
| `pull_request` into `native` | `native`, `native-tsan`, `native-windows`, `native-macos`; `changes`, then `runner` if it says so (the Python tests are `ci.yml`'s job on PRs) |
| `workflow_dispatch` | `tools`, `native`, `native-tsan`, `native-windows`, `native-macos`, and `runner` always |

A newer push to a `wp/` branch (or to a PR) cancels the older run of the same ref; runs on `native` are never cancelled.

## Jobs

- **`tools`** (pushes and dispatch): the steps of `ci.yml`: Python 3.12, `clang lld llvm`, `pip install -r requirements.txt`, `python -m pytest -q`, and the guard that fails if `git ls-files` lists game data.
- **`native`** (N1-01; on every trigger, `ubuntu-24.04`): installs `clang lld llvm cmake ninja-build libvulkan-dev mesa-vulkan-drivers glslang-tools spirv-tools` and `pip install -r requirements.txt` (the ARM test programs are built with `tools/difftest.py`), then configures `native/` with the one configure line of `wp/N1.md`, builds, runs `ctest`, runs `python3 tools/native/check_native_deps.py` (nothing under `native/` may use Azahar), and runs `tests/test_conformance.py` with `MH4N_RUNNER` set to the native runner it just built (the ARM conformance programs on `mh4u_native_runner`, except those listed in `NATIVE_NOT_YET`; `docs/native/runner.md`). The step "Vulkan probe on lavapipe" (N2-24) runs `build/native/bin/mh4n_vkprobe` (`mesa-vulkan-drivers` makes lavapipe a device), prints its table, fails unless the table has a `device:` line naming `llvmpipe`, and checks that the probe's own `--json` read back by `--from-json` gives the same table (`docs/research/vkprobe.md`).
  - **RHI tests under the validation layer** (N2-25): the job also installs `vulkan-validationlayers`, sets `MH4N_REQUIRE_VULKAN=1` and `MH4N_REQUIRE_HEADLESS_SURFACE=1` in the `Test` step (`MH4N_REQUIRE_VULKAN=1`: a Vulkan test fails instead of skipping if lavapipe disappears, and means only that a device must exist; `MH4N_REQUIRE_HEADLESS_SURFACE=1`, N2-32: the four cases that need `VK_EXT_headless_surface` fail instead of skipping when the loader lacks it, which on the lavapipe stack means the setup broke; without it they skip with a message, as on a real GPU's driver stack that does not list the extension) and then runs `python3 tools/native/vk_layer_run.py --build build/native -R '^(rhi_.*|gpu_backend_.*|gpu_queue_test|present_test|swapchain_test)$'`, which fails on any validation-layer message (`docs/native/rhi.md`).
- **`native-tsan`** (N2-29; on every trigger, `ubuntu-24.04`): installs `clang-18 lld llvm cmake ninja-build libclang-rt-18-dev libvulkan-dev mesa-vulkan-drivers` (the compiler and the ThreadSanitizer runtime are the same major version), configures a second tree `build/tsan` with `clang-18` and `-fsanitize=thread` in the C, C++ and linker flags (otherwise the one configure line of `wp/N1.md`), builds only the test binaries that `ctest -N -R '^(rhi_.*|gpu_backend_.*|gpu_queue_test|present_test|swapchain_test)$'` lists (the regex is the `native` job's layer step; names that do not exist yet match nothing) and runs them with `MH4N_REQUIRE_VULKAN=1` and `TSAN_OPTIONS=halt_on_error=1:suppressions=tools/native/tsan.supp`; the first ThreadSanitizer report fails the job. `tools/native/tsan.supp` names only the Vulkan loader and lavapipe's driver library, as `race:` and `mutex:` entries (they are load-bearing on a busy runner and hide any report with a frame in those libraries: `docs/native/rhi.md`, "The ThreadSanitizer job"). The control D2 (a race on purpose) is not run.
- **`native-windows`** (N1-22; `windows-latest`, steps run in bash): Python 3.12 and `pip install -r requirements.txt`; llvm-mingw, fetched by `build_game.fetch_compiler` (the archive `LLVM_MINGW_URL` names in `tools/build_game.py`) into the absolute folder `build/toolchain` (its progress output goes to stderr, the step reads only the folder of the compiler it returns, checks that the compiler is there) and puts that folder on `PATH` (the runner needs its `libc++.dll` and `libunwind.dll` at run time); Ninja from the image (Chocolatey if missing). Configure is the one configure line with `x86_64-w64-mingw32-clang` and `-clang++`. Then build (`cmake --build build/native -- -k 0`: ninja keeps going, so one run lists every error; every step from the tests to "The packaged tools start" has `if: ${{ !cancelled() }}`, so a failing `ctest` does not hide the conformance result, and the job still ends red; the step "The packaged tools start" is the last of them, the artifact upload keeps the implicit `success()` and runs only when all of them passed, and not on pull requests; the artifact `mh4n-runner-windows` carries llvm-mingw's runtime DLLs (Apache-2.0 with LLVM exceptions) without their licence texts: it is for the maintainer's measurements, and the packaging of N3 must ship the notices), `ctest` with `MH4N_REQUIRE_TEST_DATA=1` (there are no Vulkan-device tests yet; the N2 tests will skip without a device), `tests/test_conformance.py` with `MH4N_RUNNER` set to `mh4u_native_runner.exe`, and `check_native_deps.py`. The test program of `cpu_test` and the code libraries of the conformance programs are PE DLLs built with the same llvm-mingw; `native/src/cpu/CMakeLists.txt` keeps the `.so` file names that `cpu_test.cpp` and `tests/test_conformance.py` use (`LoadLibraryExW` takes any file name), and the conformance step sets `CCC_OVERRIDE_OPTIONS=^--target=x86_64-w64-mingw32` so the test's plain `clang` builds for Windows. Windows notes for code in `native/`: a file that includes `<windows.h>` defines `WIN32_LEAN_AND_MEAN` and `NOMINMAX` first, and a file that includes `<windows.h>` and `cpu.h` does `#undef Yield` right after the include (winbase.h defines `Yield()` as an empty macro, which turned `GuestThread::Yield` into `void ;`); other `windows.h` names we use are avoided instead (`NewEvent`, not `CreateEvent`). The Python tools that run the LLVM programs (`port/tests/build_svc_test.py`) resolve them with `shutil.which` (`difftest.tool`) and run the full path: on Windows `CreateProcess` appends `.exe` only to a name without an extension, so a bare `ld.lld` is not found although `ld.lld.exe` is on `PATH`. `native/CMakeLists.txt` sets `CMAKE_LINK_LIBRARY_USING_WHOLE_ARCHIVE` to plain `--whole-archive`/`--no-whole-archive` for MinGW, because CMake probes `CMAKE_LINKER` (not lld) and lld's MinGW driver has no `--push-state`. The same llvm-mingw release has a Linux-hosted build, so the errors of this job can be found without CI: `cmake -S native -B build/native-win -G Ninja -DCMAKE_SYSTEM_NAME=Windows -DCMAKE_C_COMPILER=<root>/bin/x86_64-w64-mingw32-clang -DCMAKE_CXX_COMPILER=<root>/bin/x86_64-w64-mingw32-clang++ -DMH4N_WERROR=ON` with `<root>/bin` on `PATH` (that cross build compiles, links and builds the PE test libraries; the binaries do not run on Linux by themselves, but with `wine` installed and `WINEPATH` set to llvm-mingw's `bin` and `x86_64-w64-mingw32/bin` every cross-built test binary passed under wine 9.0, which is a close approximation of the Windows job but not a replacement for it).
  - **Artifact `mh4n-runner-windows`** (pushes and dispatch, not pull requests; 30 days): `mh4u_native_runner.exe`, `mh4n_ipc_replay.exe` (the IPC replay), `mh4n_capture_player.exe` (the capture player) and `mh4n_vkprobe.exe` (the Vulkan probe, N2-24; it loads `vulkan-1.dll` at run time, so no Vulkan file is in the artifact), and the llvm-mingw DLLs they import, directly or through another DLL (found with `llvm-objdump -p` over the four programs, looked up in llvm-mingw's `bin/` and in `x86_64-w64-mingw32/bin/`; each DLL once), all in one folder, so the four command-line tools run on any Windows PC without a build. No game data is in it (they are our binaries); the three diagnostic tools are stripped of debug information (`RelWithDebInfo` keeps about 35 MB of DWARF inside each MinGW executable), the runner is packaged as it was, and the step lists the files and the folder's size. The step "The packaged tools start" runs each of the four with a `PATH` that has only the Windows folders and checks that `--help` prints its usage (`usage: mh4u_native_runner`, `usage: mh4n_ipc_replay`, `usage: mh4n_capture_player`, `usage: mh4n_vkprobe`) and exits 0, for all four in one run, and fails naming each tool that did not. `mh4n_hdpack` is not in it. Fetch it like the Linux runner's, with the artifact name `mh4n-runner-windows` (`gh run download <run> -n mh4n-runner-windows`).
- **`native-macos`** (N1-22; `macos-26`, the label `macos.yml` uses; arm64): Xcode's `clang` and `clang++` build `native/` (one configure line plus `-DCMAKE_OSX_DEPLOYMENT_TARGET=13.3`); `brew install ninja llvm lld` supplies the LLVM tools the ARM test programs and code libraries call (`ld.lld`, `llvm-objcopy`, `llvm-readelf`, `llvm-nm`). `$GITHUB_PATH` prepends, so Homebrew's whole `llvm/bin` is not put on it (its `clang` and newer libc++ would win over Xcode's, and the vendored {fmt}, which must stay as upstream, does not compile against that libc++: it uses `malloc`/`free` without `<cstdlib>`); the step puts symlinks to just those four tools in `$RUNNER_TEMP/llvm-tools` and adds that folder. Then build (`-- -k 0` and the same `if: ${{ !cancelled() }}` on the later steps, as on Windows), `ctest` with `MH4N_REQUIRE_TEST_DATA=1`, `tests/test_conformance.py` with `MH4N_RUNNER`, and `check_native_deps.py`. The step "The Vulkan probe starts" (N2-24) prints `file` and `lipo -archs` of `build/native/bin/mh4n_vkprobe`, fails unless it is an arm64-only executable, prints the build version of the executable (`vtool -show-build`, or `otool -l` if there is no `vtool`; a missing tool is not a failure) and checks that `--help` prints `usage: mh4n_vkprobe` (the runner has no Vulkan driver, so the probe is started, not run on a device); the step "Upload the Vulkan probe" publishes that one file as the artifact `mh4n-vkprobe-macos` (30 days; pushes and dispatch, not pull requests; `if-no-files-found: error`). The file is an unsigned arm64 executable built on macOS 26 for macOS 13.3 or later (the job's configure line sets `CMAKE_OSX_DEPLOYMENT_TARGET=13.3`: 13.0 failed to compile `ptm_gamecoin_test`, whose doctest stringifying of a file time needs `std::to_chars` for floating point, first available in 13.3; the start-check prints the executable's `minos`; if it still does not start, the maintainer runs `vulkaninfo --json` from the Vulkan SDK and sends that file: `mh4n_vkprobe --from-json` reads it on any machine); it has no library beside it (it loads the Vulkan loader or MoltenVK at run time); the zip of an artifact drops the executable bit and a browser download is quarantined, so the maintainer runs `chmod +x mh4n_vkprobe` and, if macOS refuses it, `xattr -d com.apple.quarantine mh4n_vkprobe` (`docs/research/vkprobe.md`). The log prints the page size of the machine (16 KiB on Apple silicon; `native/src/memory` works in host pages, so `memory_test` asserts per-page faults only where the host page is 4 KiB and, on a coarser host, what the module guarantees there: a freed guest page inside a mapped host page stays accessible and reads zero, and only a whole released host page faults).
- **`changes`**: decides whether `runner` is needed, from the files changed under `port/`, `tools/`, `config/` and `.github/workflows/native.yml`:
  - dispatch: always;
  - PR: the files of the PR (`base...head`);
  - push to `wp/**`: the files changed since the merge base with `origin/native`;
  - push to `native`: the files of the pushed commits (`before..HEAD`); a new branch or a force push, where `before` is unusable, builds.
- **`runner`**: the reference runner, in the container image `linux.yml` uses (`opensauce04/azahar-build-environment:latest`).
  1. Azahar is cloned and checked out at `port/azahar/COMMIT`, submodules fetched, `port/azahar/azahar.patch` applied.
  2. ccache through `actions/cache`, keyed on the hash of `COMMIT` and the patch (plus the commit sha; the restore key is the hash alone).
  3. Configure with the flags of `port/README.md`'s Linux runner build (no Qt, no Vulkan or OpenGL, no SDL2, software renderer), build target `mh4u_runner`.
  4. Package `mh4u_runner`, every shared library `ldd` resolves except the C library's own, and `run.sh` (sets `LD_LIBRARY_PATH` to the bundled `lib/`) into `mh4u-runner-linux.tar.gz`; a step unpacks it and checks `run.sh --help` prints `usage: mh4u_runner`.
  5. Upload as artifact `mh4u-runner-linux`, kept 30 days.

## The app tree: `native-app.yml` (N2b-27)

The workflow is `.github/workflows/native-app.yml` ("Native app CI"). It builds and tests `native/` with `-DMH4N_APP=ON` (rule 2 of `wp/N2b.md`; [`app.md`](app.md)), which needs SDL3. `native.yml` does not: its configure line has no `MH4N_APP`, so the runner's jobs never need SDL3. Nothing in `native-app.yml` installs SDL2 (SDL2 and SDL3 export the same function names, ROADMAP §4), and it never uses game data.

| Trigger | What runs |
|---|---|
| `push` to `native` or to a `wp/**` branch | `app-linux`, `app-windows`, `app-macos`; the Windows artifact is uploaded |
| `pull_request` into `native` that touches `native/**`, `port/app/**`, `port/src/**`, `tests/test_native_app*.py` or the workflow | the three jobs; no artifact |
| `workflow_dispatch` | the three jobs and the artifact (the orchestrator dispatches it on a batch branch before a maintainer procedure: `gh workflow run native-app.yml --ref <branch>`) |

The concurrency group is workflow plus ref, and `cancel-in-progress` is on except on `native`: a newer push to a `wp/` branch or a PR cancels the older run, and so does a `workflow_dispatch` on the same ref, so dispatch only after the push run has finished. `permissions` is `contents: read`, and the checkouts do not persist credentials.

**SDL3.** Each job clones `libsdl-org/SDL` at the tag `release-3.4.18` (`SDL_TAG`, one place at the top of the file; D8), builds it with the job's own toolchain (`-DCMAKE_BUILD_TYPE=Release -DSDL_TESTS=OFF`, as `tools/native/setup_env.sh`) into `build/sdl3`, and restores that folder with `actions/cache/restore@v4` and, on a miss, saves it with `actions/cache/save@v4` right after the install (not by the combined action's post-job step, which runs only when the whole job is green, so a red run would rebuild SDL3 on every retry): the key starts with `sdl3-${SDL_TAG}`, then the system (`linux-ubuntu24.04-clang`; `windows-llvm-mingw-` and the hash of `tools/build_game.py`, which names the llvm-mingw release; `macos-arm64-xcode-clang-13.3`), so a new tag or a new compiler builds it again and nothing else does. A cache hit skips the clone, the build and (Linux) the apt headers. `CMAKE_PREFIX_PATH` is set to the folder through `$GITHUB_ENV`, and the Configure step then checks that `SDL3_DIR` in `CMakeCache.txt` points into `build/sdl3`, so a system copy cannot be used by mistake.

**Jobs**
- **`app-linux`** (`ubuntu-24.04`): the packages of `native.yml`'s `native` job (`clang lld llvm cmake ninja-build libvulkan-dev mesa-vulkan-drivers glslang-tools spirv-tools`; `mesa-vulkan-drivers` is lavapipe) plus, on a cache miss, the X11, Wayland and audio headers SDL3 needs to build (the list of `ENV.md`); `pip install -r requirements.txt` (the ARM test programs); configure (the runner's line plus `-DMH4N_APP=ON`, in `build/native-app`), build, `ctest --test-dir build/native-app --no-tests=error --output-on-failure` with `MH4N_REQUIRE_VULKAN=1` and `MH4N_REQUIRE_TEST_DATA=1`; a step that runs `build/native-app/bin/mh4n_vkprobe` and fails unless a `device:` line names `llvmpipe` (so "requires Vulkan" means lavapipe); `mh4u-native --version` must print `mh4u-native <revision>`; and the step of N2b-10's end-to-end test, `if [ -f tests/test_native_app.py ]; then MH4N_APP_EXE=build/native-app/bin/mh4u-native MH4N_REQUIRE_TEST_DATA=1 python3 -m pytest -rs tests/test_native_app.py; fi`. Until N2b-10 adds the file the `if` does nothing, and a second line of the step prints `tests/test_native_app.py does not exist yet: skipped by its if`; once it exists the test runs with `-rs`, and its skips are listed.
- **`app-windows`** (`windows-latest`, steps in bash): llvm-mingw from `tools/build_game.py` (the step of `native-windows`, copied), SDL3 built with it (`x86_64-w64-mingw32-clang`; not MXE), its `bin` folder put on `PATH` for the tests (the tests start `mh4u-native.exe` from the build folder), configure with `x86_64-w64-mingw32-clang`/`-clang++`, build with `-- -k 0`, `ctest --no-tests=error` with `MH4N_REQUIRE_TEST_DATA=1`, `mh4u-native.exe --version`; every step after the build has `if: ${{ !cancelled() }}` as in `native-windows`. No Vulkan device on this runner: the tests that need one skip there.
- **`app-macos`** (`macos-26`): Xcode's clang (never Homebrew's: `brew install ninja llvm lld` and the folder of four symlinks, as `native-macos`), SDL3 built with it for `CMAKE_OSX_DEPLOYMENT_TARGET=13.3` (the same value as the app's configure line), configure, build, `ctest --no-tests=error`, `mh4u-native --version`.

**Artifact `mh4u-native-windows`** (`app-windows`; pushes and dispatches, not pull requests; 30 days; `if-no-files-found: error`). The step "Package mh4u-native and its DLLs" copies `mh4u-native.exe`, `mh4u_native_runner.exe` and `mh4n_hdpack.exe` (only `mh4n_hdpack.exe` is stripped of debug information; `mh4u-native.exe` and `mh4u_native_runner.exe` keep theirs, for crash reports) and `SDL3.dll` into `app-windows/`, then adds every llvm-mingw DLL those programs import, directly or through another DLL, with the loop of `native-windows` (`llvm-objdump -p`, looked up in llvm-mingw's `bin/` and `x86_64-w64-mingw32/bin/`, each once). It prints each program's imports, so the log says which DLLs were needed. The spec calls the content "five files": that is the four programs and DLLs, plus the llvm-mingw runtime DLLs the closure finds (see *Count* below). The step "The packaged programs start" runs each program with a `PATH` of only the Windows folders (no llvm-mingw, no `build/sdl3/bin`): `mh4u-native.exe --version` must print `mh4u-native ` and exit 0, `mh4u-native.exe --help` `usage: mh4u-native` and exit 0, `mh4u_native_runner.exe --help` `usage: mh4u_native_runner` and exit 0, and `mh4n_hdpack.exe --help` `usage: mh4n_hdpack` with exit 2 (the tool has no `--help` option; it prints its usage for an unknown option, which is how a packaged start is told from a missing DLL). All four are tried and then the step fails; the upload runs only if the whole job passed. The maintainer's download and smoke test are in [`app.md`](app.md).

**Count.** The spec says "the five files" (the two programs the maintainer runs, the runner, the HD tool, `SDL3.dll`) but also "the llvm-mingw DLLs they need", which are not a fixed number. A cross build with the same llvm-mingw release (20241217, ucrt) and SDL3 3.4.18 on Linux showed the closure: `mh4u-native.exe` imports `SDL3.dll`, `libc++.dll` and `libunwind.dll` (and Windows system DLLs); `mh4u_native_runner.exe` the same two; `SDL3.dll` only Windows system DLLs (the UCRT `api-ms-win-crt-*.dll` are Windows', not copied); `libc++.dll` imports `libunwind.dll`. So the artifact has **six files**: the five of the spec (`mh4u-native.exe`, `SDL3.dll`, `mh4u_native_runner.exe`, `mh4n_hdpack.exe`, and, counted as one, "the llvm-mingw DLLs") with the DLLs being two, `libc++.dll` and `libunwind.dll`. The step prints the real list in the run's log; if it differs, `app.md`'s expected list is what to update.

## Fetching the runner (cloud session)

The newest runner that still has its artifact, for a branch (`<branch>` is `native` or a `wp/...` name). From a cloud session this needs the environment to allow the host GitHub serves artifacts from, `*.blob.core.windows.net` (the download fails with `Forbidden` otherwise; see `AGENTS.md` §7):

```bash
id=$(gh api 'repos/CompaLarios18/MH4UltimateDC/actions/artifacts?name=mh4u-runner-linux&per_page=50' \
  --jq '[.artifacts[] | select(.expired | not) | select(.workflow_run.head_repository_id == .workflow_run.repository_id) | select(.workflow_run.head_branch == "<branch>")][0] | .workflow_run.id')
case "$id" in ""|null) echo "no runner artifact for <branch>"; exit 1 ;; esac
mkdir -p build/runner
gh run download "$id" -n mh4u-runner-linux -D build/runner
tar -xzf build/runner/mh4u-runner-linux.tar.gz -C build/runner
build/runner/run.sh --help        # prints the runner's usage
```

Only pushes (to `native` and `wp/**`) and dispatches publish the artifact, never pull requests, and the recipe also requires the run to come from this repository (a fork's branch can carry any name). A push that changed none of the watched paths builds no runner, so the newest artifact of a branch may come from an earlier push: compare the run's `head_sha` (`gh run view <id> --json headSha`) with `git rev-parse <branch>` when it matters, and for a branch without a runner use `native`'s, or dispatch one (`gh workflow run native.yml --ref <branch>`).

## Building it when there is none

```bash
gh workflow run native.yml --ref native
gh run list --workflow native.yml --branch native --limit 1     # then: gh run watch <id>
```

GitHub accepts a dispatch for a workflow that is not on the default branch once it has run at least once. Dispatch always builds the runner. Artifacts expire after 30 days, so a quiet branch needs this now and then.

## Not covered

The port's Windows and macOS builds of Azahar (`windows.yml`, `macos.yml` on `main`; dispatch them with `ref` set to any branch); the native runner's own are `native-windows` and `native-macos` above. The game-data guard of N0-19 is its own workflow, `native-guard.yml`: it runs `tools/native/check_no_game_data.py --range` over the pushed or proposed commits, on the same triggers (pushes to `native` and `wp/**`, PRs into `native`). On a PR it runs the script of the base branch (`git show <base>:tools/native/check_no_game_data.py`), so a PR cannot weaken the check that judges it; until the base has the script (the PR that introduces it), it uses the PR's own. The allowlist `config/native/large_files.txt` is still the PR's: each entry needs a path and a SHA-256 and is reviewed. A PR can still change the workflow files themselves, so review changes to `.github/workflows/` like code that guards the repository. Both workflows set `persist-credentials: false` on every checkout, so the read-only token is not left in `.git/config` while PR-controlled scripts run.
