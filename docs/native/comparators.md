# The comparators: what each rule compares, and what it still catches

Written by N0-25 (D30, D31, D34) and extended by N0-32 (D50, D51, D52: sections 7 to 9), N0-33 (D76: the `native` profile, section 10) and N0-36 (D82: what the quest sessions' `fs:` reads show and why no rule absorbs it yet, section 11). The tools: `tools/compare_svc_traces.py` (system calls), `tools/native/state_diff.py` (game state), `tools/compare_ipc_traces.py` (IPC), `tools/native/capfmt.py` (the HID and DSP captures), `tools/native/cross_model_report.py` (N0-28: the report of the cross profile's numbers), `tools/native/golden.py` (N0-09: runs them). The trace formats are in [`wp/N0.md`](wp/N0.md) (*Rules shared by the N0 packages*) and `tools/native/tracefmt.py`. Every comparator prints only service names, SVC numbers, register names, result codes, thread names and counts: its output can be quoted. The traces themselves are game data and stay in `build/`.

## 1. The profiles (D31, D76)

| Profile | Compares | Svc comparison | State comparison |
|---|---|---|---|
| `same`: two runs of one backend (`--cpu recomp` twice; later the native runtime's deterministic mode twice) | exact; no tick tolerance | all calls, in order, with `--normalize --outputs`. Fallback only, if N0-29 cannot remove the tick jitter (D30): `--collapse-polling config/native/svc_polling.txt` | `state_diff.py --tolerance 0 --min-changes <recorded>` |
| `cross`: two timing models (`jit` against `recomp`, the reference against the native runtime) | what a different clock cannot change | only the calls of `config/native/svc_cross_model.txt` (`--cross-model`); the full trace is information | `state_diff.py --tolerance 4 --min-changes` and the margin guard of 60 frames (D50, section 9); IPC per thread with `config/native/ipc_time_dependent.txt`, the `fs:USER/file` Reads as multisets and the masked Writes (D52, section 7); HID; DSP aligned on its first buffer change (D51, section 8) |
| `native` (D76): the native runtime in real time against the reference, asked for with `--profile native` | the cross profile for a game clock that follows the host while the reference charges the modelled 268 MHz | as `cross` | as `cross` with `--tolerance 24` (the margin guard of 60 stays); IPC as `cross` with the touching `fs:USER/file` Reads merged before the multiset (`--fs-reads-coalesce`, `--fs-reads-prefix`, section 10); DSP aligned with `--max-shift 300` and, for an odd shift, the two regions swapped (section 10) |

Once N0-26 and N0-29 are done, a `same` comparison needs no rule: the text traces are identical apart from their first line.

## 2. `compare_svc_traces.py --collapse-polling FILE`

`FILE` (`config/native/svc_polling.txt`) lists the calls whose result depends only on the clock and that change nothing, one per line, `<svc hex>  # reason`. It holds `0x28` (GetSystemTick) and nothing else. Use it with `--normalize --outputs`.

In each thread, a maximal run of consecutive calls of one listed svc becomes one record. Two records match when:

- both are runs of the same svc and the first call of each was made from the same place (`pc` and `lr`);
- the places of the shorter run (the `pc` and `lr` of its calls) are all places of the longer one; runs of one length must have the same places (a longer run is a shorter one plus more iterations of the loop, which may pass places the shorter one never reached);
- nothing else is compared: not the lengths (they are printed: per thread, the number of runs and the longest run on each side), not the registers or `t=` of the calls in a run. The registers of a polling call carry what the call before it left, for example those of a `SleepThread` that just returned.

Every other call compares as without the flag, in order: svc, `pc`, `lr`, the arguments, and with `--outputs` the results. `--in4` is not added to the collapse: in every `SleepThread` call `r6` holds the high word of the last GetSystemTick result, which is not an argument of the call and differs between runs.

**What it still catches.** A polling call changes nothing, so a run can only matter through the code that makes it and through the calls around it, and both are compared: a run on one side with no run at that place on the other (the next record is a run on one side and a call on the other); a run that starts somewhere else; a shorter run that passes a place the longer one never does; a non-polling call missing, added, moved, or with another argument or result between two runs (the two runs then merge on one side and are two records on the other). What it cannot catch: the number of iterations of a polling loop (that is the clock), and a difference in the registers of a polling call.

**What it does not cover.** The `SleepThread` durations that the game derives from the clock (whole milliseconds). They are compared like any call and still differ, see the measurement below. The fallback can therefore pass only if N0-26 or N0-29 remove that difference.

## 3. `compare_svc_traces.py --cross-model FILE`

`FILE` (`config/native/svc_cross_model.txt`) lists the calls compared between two timing models, one per line: `<svc hex> in=<regs> out=<regs>  # reason`. The registers listed are the ones that ARE compared (`config/native/svc_unused_registers.txt` lists the ones that are ignored). `in=` takes `r0`-`r6` (`r4`-`r6` come from the trace's `in4=` field) and `out=` takes `r0`-`r3`. The option implies `--normalize` and cannot be combined with `--collapse-polling`, `--in4` or `--ignore-args`.

- **Calls.** The criterion: calls that create, map, unmap, duplicate or close kernel objects or memory, or start or end a thread, and whose result depends neither on time nor on another thread's progress. The file holds ControlMemory, CreateThread, ExitThread, CreateMutex, CreateSemaphore, CreateEvent, CreateTimer, CreateMemoryBlock, MapMemoryBlock, UnmapMemoryBlock, CreateAddressArbiter, CloseHandle, DuplicateHandle and ConnectToPort, each with its reason. Never waits, sleeps, signals, arbitration, the clock or SendSyncRequest. The registers follow the SVC wrapper (Azahar's `svc_wrapper.h`, as `native/src/kernel/svc.cpp` documents it): the result is `r0`, the values an output pointer receives follow in `r1` up, and the inputs keep their positions with the output pointers' slots skipped, so the slot of an output pointer (`r0` of CreateEvent, for one) holds a stack address the caller left and is never listed.
- **Kernel-chosen addresses are never compared.** Which address an allocation gets depends on the order in which threads allocate, which differs between timing models. For ControlMemory that is the operation (`r0`), the size (`r3`) and the permissions (`r4`), and the result code; not `r1` and `r2` (addresses taken from an earlier result, or a hint) and not the address it returns. For CreateMemoryBlock and MapMemoryBlock: sizes, permissions, the handles and the result, not the address, because a trace cannot tell a constant of the game's code from one returned by an earlier call. A thread's argument and stack top (CreateThread `r2`, `r3`) are heap addresses and are not compared either; the entry point, priority and processor id are.
- **Compared per call.** `svc`, `pc`, `lr` and the result code (`out r0`) always; the listed inputs; the listed outputs with `--outputs`. Handles are compared by their normalised name. Each thread's sequence is filtered to the listed calls and compared in order, with `--prefix` as in the plain comparison.
- **Names across models.** Threads are `main`, and otherwise `<parent name>/<entry>#<k>`, where k counts the threads that parent created with that entry, in its own order (from the `parent=` of the `# thread` lines). `tracefmt.py`'s global `<entry>#<k>` can swap two threads with the same entry created by different parents when the interleaving differs; the per-parent name cannot, because one parent creates its threads in program order. Handles are `<kind>#<creating thread>.<k>`, k counting per creating thread and kind from 0, so creations interleaved differently across threads keep their names. A handle that came in an IPC reply is `?` (this tool does not read the IPC trace).
- **Output.** Per thread: the number of compared calls on each side and, for information, each side's total number of calls.

**What it still catches.** A creation, map, unmap, duplicate, close, thread start or thread end that one model does and the other does not, or does at another place, with another size, permission, operation, priority, entry point or processor id, or with another result code; a thread that one model never creates (its parent's CreateThread is missing, and the thread's own listed calls too); the order of one thread's own listed calls. What it cannot catch: anything about waits, sleeps, signals, arbitration, SendSyncRequest and the clock (those run a different number of times in two timing models: the IPC trace, the state checkpoints, HID and DSP cover what they cause); which address the kernel handed out; a thread that makes no listed call (it is only visible through its parent's CreateThread).

## 4. `state_diff.py --min-changes N`

`state_diff.py` aligns two state traces on the scene byte (`scene`): the k-th scene change of one with the k-th of the other, and compares, at each aligned change, the scene reached, the frame (within `--tolerance`) and the `eq` observables of `config/native/observable.txt`. It counts the first record as a scene change, so a trace whose scene never changes agreed with itself (D34, M7).

`--min-changes N` (default 0: no minimum) exits 3 and prints how many it aligned when fewer than N **real** scene changes were aligned in the reference trace. A real scene change is a record whose `scene` is readable (not `-`) and differs from the previous readable `scene`; the first record, a change from `-` to a value (every trace starts with `scene=-`, then a value) and a change to `-` are not real. The alignment and the statuses 0 and 1 are unchanged; a divergence wins over 3. The final line prints the number of real changes.

**What "state passed" means.** `state_diff.py` compares the `eq` values only at the aligned scene-change records. `stage_loader_state` and `quest_id` are therefore not checked inside a scene, and G1, G2 and G6 have no quest, so there is no `quest_id` to check. A passed state comparison means: the scene sequence, the frames of its changes within the tolerance, and the values of the `eq` observables at those records. No more.

## 5. Exit statuses (svc and state; the IPC and capture tools have their own, below)

| Status | `compare_svc_traces.py` | `state_diff.py` |
|---|---|---|
| 0 | every thread matches | the traces agree (and at least `--min-changes` real changes) |
| 1 | a thread differs (the first difference per thread is printed; with `--collapse-polling` or `--cross-model` also every record that differs at the same position, up to 20 per thread, with the names of the fields) | a divergence (the first is printed) |
| 2 | a trace or an option file cannot be read, holds no system call, or an option is wrong | bad input |
| 3 | nothing was compared: after the `--cross-model` filter neither trace has a call to compare (D34) | fewer than `--min-changes` real scene changes were aligned |

A difference wins over 3. `golden.py check` (N0-09) uses the same four statuses.

## 7. `compare_ipc_traces.py`: the `fs:` rules of D52 (`--fs-reads-multiset`, `--fs-write-mask`)

Two timing models cannot be expected to make the same number of reads, or to interleave two readers the same way, but **what a game reads from a file follows the file, and what it writes is its state** (D52). The cross profile of `golden.py` and the native runtime's checks (N1-21, N1-26) run `compare_ipc_traces.py` with these options; no `fs:` command goes in `config/native/ipc_time_dependent.txt`.

- **`--fs-reads-multiset [--max-surplus N]`** (default 16). Per thread, the Read requests of the file sessions of `fs:USER` (`fs:USER/file`, header `0x080200c2`) are taken out of the thread's list and compared as a multiset of **(offset, size, result, CRC-32 of the data the reply wrote)**, order ignored. The multiset of the side with fewer reads must be contained in the other side's, and the other may hold at most `--max-surplus` more. So five reads fewer (a reader cut short by the end of the run or a scripted skip) and two reads in another order pass; a surplus of 17, a read of another offset or size, a read that returned other data, or a read with another result fails, and so, since N0-37, does a file session that one side reads from and the other does not (whatever its size) and a thread whose Reads cover more than a bound of bytes that the other side does not (section 12). (The result is part of the key on top of the three values of D52: it can only make the rule stricter.) The report names the offsets, sizes, result and CRC of the first reads the other side lacks, never the data.
- **`--max-one-sided BYTES`** and **`--max-detached BYTES`** (N0-37, both profiles) bound what the Reads of a thread cover, and a file session read by one side only is a difference: section 12.
- **`--fs-reads-coalesce`** and **`--fs-reads-prefix`** (D76 and N0-33, the `native` profile only) change what the multiset holds: section 10.
- **Everything else of the `fs:` sessions is compared in order and in full**: with the option, a request of any `fs:` session (a Write above all) must also have the same header and **normal parameters** in the request and in the reply (an offset, a size, flags, a path's size, a handle's number) as its counterpart, besides the session, header, result and descriptors (the CRC-32 of a Write's data is a descriptor). The words after the normal parameters are translate parameters (descriptors, handles, the address of a buffer, which the process chooses and a different clock can change), so they are not compared. Requests of services that are not `fs:` are compared as before (the plain comparison reads no word).
- **`--fs-write-mask FILE --fs-write-mask-session S`**. `FILE` is `config/native/fs_write_masks.txt`: one line per byte range, `<session> <write-size> <write-offset> <mask-offset> <mask-size>  <reason>`, written by the orchestrator when a work package proves a range depends on the clock (N0-31 proved the two ranges of G2's save). A Write of a file session whose size and file offset are those of a line of session `S` is compared by the CRC-32 of its data **with the masked ranges set to zero**, on both sides; a byte that differs outside a masked range still fails. The trace must hold the Write's data (`--trace-ipc-full`: `data=`). The lines of other sessions are not looked at; `golden.py` passes the session of the recording.
- **Errors, never a pass** (exit 2): a mask file that is missing, is not UTF-8 text, holds no line or a malformed line (a missing reason, a negative number, a range that is empty or outside the Write); a line of session `S` that matches no Write of either trace; a Write that a line applies to whose trace has no data for it, or whose data does not match the CRC-32 the trace recorded for it. `--max-surplus` without `--fs-reads-multiset`, one of the two mask options without the other, and a negative number are usage errors (also exit 2).
- The output ends with `fs reads: ...` (threads that read, reads on each side, the largest difference), `fs coverage: ...` (N0-36, section 11: the bytes that only one side covers; N0-37 applies limits to them per thread, section 12) and `fs write masks: ...` (lines of the session and Writes they applied to); `golden.py` prints them with the result of `ipc`.

**What it still catches.** A read that returns other bytes, another offset or size, or fails; more than 16 reads beyond the other side (a loop that reads in a runaway); a thread, or a file session of a thread, that reads on one side only, and Reads that cover bytes the other side does not beyond the bounds of N0-37 (section 12); every `fs:` command that is not a Read, in its order and in its normal parameters; a Write with any byte different outside the masked ranges, or with a different size, offset or flags. **What it cannot catch.** The order of the reads of one thread (D52 drops it), and how many reads a thread makes up to the surplus; a difference inside a masked range (that is what the mask is for: the reason of each line says why).

## 8. `capfmt.py diff-dsp --align [--max-shift 48]`: the DSP capture across timing models (D51, D76)

`diff-dsp` keys on the DSP's own frame counter, which is the model's clock: on `jit` the same audio stream plays a constant number of DSP frames later than on `recomp` (22 in G1, N0-28). `--align` compares the content:

1. the **first enabled source** is the lowest-numbered source that is enabled, in the region the DSP reads, in the first frame of the reference that has one;
2. the first change of that source's buffer id in the reference is looked for in the candidate **by its id** (a capture may start in the middle of a stream: the candidate's first changes can be buffers the reference started after), and the difference of the two DSP frame counters is the **shift**;
3. the shift must be at most `--max-shift` DSP frames (default 48, about 233 ms) in either direction;
4. it must be **constant**: every other buffer change of that source inside the overlap (one frame in from each end) has its counterpart, with the same id, at the shift within 1 frame, and the candidate has no change the reference lacks;
5. after the shift, every source status block of both regions of every overlapping DSP frame (enabled, dirty, sync count, buffer position, current and last buffer id) must be equal. The PCM samples and the sample data are not compared across models (the native runtime has no mixer). **An odd shift swaps the regions** (D76, N0-33): the two regions alternate with the DSP frame counter (the region of the counter's parity is the one the DSP reads: 300 of 300 frames of G1's recording and of both native runs), so when the shift is odd the reference's region *r* is compared with the candidate's region *1 − r*, the one that holds the same DSP frame; with an even shift the regions are compared as they are. Without the mapping an odd shift fails on every block (the reference's current frame against the candidate's previous one); the mapping does not make a stream pass that is not the same, because the status blocks are still compared field by field. The printed shift says when the mapping was used, and a difference names both regions;
6. the shift is printed, with the buffer and frames it was found on, the numbers compared and the largest deviation, on success and on failure. Exit 0 equal, 1 any failure above, 2 a file that is not a DSP capture; `--max-shift` without `--align`, a negative bound and `--align` with `--frames` are usage errors.

When neither capture has an enabled source, or the source never changes buffer in either, there is nothing to align on: the comparison is the plain one (shift 0, keyed on the counter) and says so; if only one side has an enabled source, or only one side has buffer changes, or no buffer id is in both, it fails. On G1's two captures (the recording and the first `jit` run): shift +22, 293 DSP frames and 14064 status blocks compared, all equal, 85 buffer changes at the shift with a deviation of 0 frames; `--max-shift 10` exits 1.

## 9. The cross profile's state comparison and its margin guard (D50)

The cross profile runs `state_diff.py --tolerance 4 --min-changes <the recording's real scene changes>` (the same profile stays at `--tolerance 0`): a real scene change may fall up to 4 frames apart on the two models, to the same scene and in the same order. On top of it, `golden.py` adds the result `state-margin`, with `cross_model_report.py`'s logic: every input event of the session script that follows a real scene change must come **at least 60 frames** after the last real scene change on **both** sides, so that a shift of a scene change can never move an input into another scene. An input before the first real scene change has no margin. Both numbers can be changed in the cross and native profiles only (`golden.py check --tolerance N --min-margin N`; the native profile's tolerance is 24, D76, its margin guard the same 60); `--require state` covers `state-margin`. The result prints the largest shift and the smallest margin of each side. The numbers are D50's: measured on 13 real scene changes in G1, G2 and G6 (largest shift 3, smallest margin 91; `docs/native/cross-model.md`).

## 10. The `native` profile (D76): what N0-33 added, and what was measured

**Why.** N1-21 ran the real game on the native runtime (G1 to the title in 31 s, G2 to the opening in about 2.5 minutes) and found the same scenes in the same order, the cross-model SVC list, the HID capture and every checkpoint equal, and four things the cross profile's numbers cannot hold, all of them the native game clock following the host while the reference charges the modelled 268 MHz: the first scene change 15 frames early, the DSP counter about 204 to 209 frames apart, a streaming reader's reads chunked differently, and (G2) one thread's reads. D76 decided the `native` profile; `golden.py check --profile native` is `cross` with the rules below and nothing else loosened. The numbers are D76's (scene changes within **24** frames, DSP shift up to **300**), the margin guard is D50's 60 on both sides, the surplus limit D52's 16, the Writes are compared in full but for the proven masks. The `same` and `cross` profiles do not change (tests keep their numbers and results).

**Odd DSP shifts** are in section 8 (the two regions alternate with the DSP counter, so an odd shift maps region *r* to *1 − r*). Measured: G1's saved native runs, shifts -204 (even) and -205 (odd), 292 and 293 DSP frames, 14016 and 14064 status blocks equal; written as before (region against the same region) the odd one differs.

**`compare_ipc_traces.py --fs-reads-coalesce`** (needs `--fs-reads-multiset`). Before the multiset is built, the Reads of one thread and one file session (`fs:USER/file#3`) whose byte ranges touch are merged into a run: the Read of the summed size, its CRC-32 the combination of the parts' (`tracefmt.crc32_combine`, equal to `zlib.crc32` of the concatenation; tested on random splits). Only a Read that succeeded, filled its buffer (the reply says it read `size` bytes) and has its CRC-32 in the trace is merged; any other Read, and a Read of no bytes, is compared on its own. The surplus limit is counted in **runs**. What it catches: a gap or a piece read twice is a difference (the repeated piece is a run more, inside the allowance as any repeated read is), a piece with another CRC-32 changes the run's CRC-32, a run that stops short or goes on is a run the other side lacks. What it cannot catch: the sizes the pieces were read in, and, because touching reads fuse, how many times a stream is read in pieces of one range.

Two details differ from the first reading of D76's text and N0-33's spec, and both were forced by the data (the saved pairs, then N0-28's `jit` runs, see below):

1. **The order of the Reads does not matter.** The spec says "consecutive reads ... in the thread's request order", with a read that does not touch the previous one starting a new run. Done so, the `jit` runs of N0-28 that the cross profile passes **fail** the native profile (G2 and G6 thread #12: two 8192-byte reads in the other order break the run on one side), and D52 itself ignores the order. A session's Reads are therefore taken by offset (then size, then CRC-32) and each joins the oldest run that ends at its offset, else starts a run. The units are a function of the multiset of Reads, so two runs that send the same Reads in another order give the same units. `tracefmt.coalesce_fs_reads` documents it.
2. **`--fs-reads-prefix`** (needs `--fs-reads-coalesce`; **not in D76's text**). A streaming reader stops where its clock says, so the run of touching Reads of a stream is longer on one side: in **every** pair measured, the `jit` ones included, the movie reader of N1-21 (thread #17) has one run of about 1.69 million bytes on both sides and the two end 8 to 10 KiB apart. With exactly equal units that is a foreign run and the profile fails. The rule: a run that the other side has no equal of is also contained when it is a prefix of a run of the other side, or that run is a prefix of it: same start and result, and a part boundary of the longer run exactly where the shorter ends, with the same CRC-32 of the bytes up to there (combined from the longer run's parts). The bytes of the longer run beyond the shorter's end are not compared with anything, so their Reads (4 to 7 per pair here) count toward the surplus limit with the other surplus; without a part boundary at that offset the longer run's data there is not known, and the runs differ (a mutated copy of G1's native trace with one CRC-32 changed in the middle of the stream, or one read removed, fails; with the last read removed or one read repeated it passes, as a shorter stream and a repeated read should). This is a design choice the orchestrator did not make: `golden.py` has it as `NATIVE_FS_READS_PREFIX`, one constant, and `golden.md` names it. With it off, G1 and G2 fail on that thread in every native pair and the `jit` pairs fail too.

## 11. The quest sessions' `fs:` reads (N0-36, D82): what differs, why, and why no rule absorbs it yet

**Status: `needs-decision`.** N0-36 was to build a rule for the cross and native profiles that absorbs the `fs:USER/file` Read differences that N0-30 found on G3 and G4 (jit against recomp). The measurement below says what they are; it also says that the variance contains whole resources, so that no number of bytes taken from the data separates it from a resource that was not loaded. No rule was built and no profile changed. What was added is information: `compare_ipc_traces.py --fs-reads-multiset` now ends its report with an `fs coverage:` line (section 7 lists the other lines), which is never gated and which `golden.py` prints with the result of `ipc`. Numbers only below; the traces are in `build/`.

**Method.** For every thread and file session, the Reads of both sides with their offset, size, result and CRC-32, the union of the byte ranges each side returned (the pieces do not matter), what both cover, and what only one covers. Run on the saved pairs of N0-28/N0-30 (`jit` against the recordings of G1, G2, G6, G3 and G4) and of N0-33 (the native runs of G1 and G2, nine pairs). Every one-sided byte of these threads is in the one file session the loaders and the streaming readers share (`fs:USER/file#1`, the game's big archive). Threads #3 and #5 also read a second file session (`fs:USER/file#3`) that covers exactly the same bytes on both sides (393,216 and 5,162,123 bytes). Everything else is equal: of the (thread, file session, offset, size) keys that both sides read, **all** have the same result and the same CRC-32 (G4: 1,160 keys; G3: 2,918, five of which one side reads twice and the other once; with the file session ignored the counts are 1,145 and 2,903). No pair of G3 or G4 has a Read with the same offset and size and another CRC-32, under any of these keyings.

**What the differences are** (from the requests; nothing was read from the game's code). The sizes, positions, counts and CRC-32 equalities are measurements; what a Read is *for* (a header, a table, the next resource) is read off the ranges, which is an inference, and the sentences say "most likely" where they depend on it.

1. *The loaders (#3, #5) do not read a resource in other pieces; they load another resource.* A load is three Reads of thread #3: 12 bytes at the start of a resource, then (most likely a table whose size the header gives; the traces hold CRC-32s, not the bytes, so this was not seen) 3,280, 560 or 80 bytes after it, then the whole resource from its start, at most 131,072 bytes in one Read (a longer resource goes on in a second Read by thread #5: 124,610 bytes after a 131,072-byte block). At two places of thread #3's request list (requests 205 to 210, the same positions on both sides and in G3 and G4; six Reads each) the two sides load **different resources whose ranges do not overlap**: the reference one of 255,682 bytes (131,072 by #3, 124,610 by #5), the candidate the next resource of the archive (79,617 bytes, all by #3); then the reference one of 2,185 bytes and the candidate the next one (2,948). A 2,185-byte resource that the reference loaded in that second place is, byte for byte (equal CRC-32), a resource that the archive also holds at another place: in G4 the reference reads only that other copy's 12-byte header and 80-byte table (as if it already held the data) and the candidate loads it in full; in G3 the reference loads it once (request 346) and the candidate twice (requests 221 and 347). The sizes of N0-30's table (3,280 + 131,072 against 560 + 79,617) are the tables and the first block of those two resources, not two ways of reading one.
2. *The streaming reader (#12) reads 8,192-byte chunks at the pace of the clock, and the streams are not the same ones at the same times.* A stream starts with small Reads (144 to 1,224 bytes) and goes on in chunks, one every 54 to 58 million ticks (0.21 s of console time) in the long ones, to within 2 % between the two sides for a stream both read in full. Most likely (an inference from the cadence of the chunks) the number of chunks is the time the stream is kept open, not a fill of a buffer or the speed of the file system. In G3's hunt the two sides start the same stream up to 1.45 billion ticks (5.4 s) apart; 5 of its 37 runs end at another place (by 1 to 26 chunks, at most 213 KB, both ways round), and one run, a stream of 2,637,824 bytes (322 chunks, a 964-byte header), is a different file of exactly the same size on each side (3.7 million bytes apart). The 30 other runs and all the chunks they have in common are equal. In G4 three streams stop one chunk apart.
3. *What the pairs have in common.* The same threads read, the same file sessions, the same number of runs of touching Reads (250 and 250 in G4; 502 and 502 in G3), the same requests in the same order everywhere else.

**Why** (an inference; no run settles it). What to load and what to play is most likely chosen from the game's own random generator, and N0-31/N0-34 (`docs/research/g2-save-bytes.md`, section 4) showed that this generator is seeded from the low 16 bits of the Unix second of the game's first clock reading (between game frames 2 and 3) and stepped once per frame; that reading falls 4.4 ms before a second boundary on `recomp` and 36 ms after it on `jit`, so **the seeds differ by one**. The tick of game frame 3 is the same in G1, G2, G3 and G4 on each backend (147,895,257 on recomp, 156,857,711 on jit: `state.txt`), so the first reading is the same one in all four sessions and the seeds differ by one in G3 and G4 as they do in G2. G1, G2 and G6 (the opening, a new game) show no such choice; G3 and G4 (the village, the Arena) do, and in a hunt the monster's own choices would add to them. That fits the picks (the other side takes the next resource of the archive, twice) and the sounds that start seconds apart. It is not proven: the reference runner has no option for a start date finer than a second, so no run with equal seeds was made. The calendar second read directly (not through the generator) would have the same effect. For the native runtime in real time the seed is that of its own first reading, whichever second that falls in.

**What the rules of D52 and D76 do with it, and what they already did not see.** The saved pairs: `cross` fails G4 on thread #3 (surplus 1, but 6 Reads of the reference have no equal) and G3 on #3 and on #12 (surplus 28, at most 16); `native` fails the same threads (G3 #12: 78 Reads beyond five runs that are a prefix of another, at most 16 allowed; six such runs over all threads of the pair; thread #3: 4 runs of the reference have no equal). The what-if controls on modified copies of passing pairs (G6 `jit`, G1 native; `build/n0-36/controls/`) show what the rules of D52 and D76 admit, which is not new but which a rule for the quest sessions must not make worse: one CRC-32 changed fails in both profiles; **a whole thread's Reads removed from the candidate passes `native` when the thread's Reads fuse into 16 runs or fewer** (the movie stream is one run: surplus 1; under `cross` the same removal fails for every thread of more than 16 Reads and passes for the ones with up to 16); the Reads of a thread with a few Reads removed pass (surplus at most 16); 10 Reads taken out of the middle of a stream pass `cross` and fail `native`; **one Read added at another offset passes `native`** (the larger side may hold 16 runs of anything; under `cross` it passes when the candidate is the larger side of that thread). So today a failed load of up to 16 runs, and an extra read of anything, are inside the allowance; D52's surplus is a count of reads (runs), not a statement about bytes. (Closed afterwards by N0-37: section 12.)

**Why no bound separates the variance from a failed load.** The coverage rule that the spec proposes (the union of the ranges per thread and file session, the CRC-32 kept where both sides read the same offset and size, a bound on what only one side covers) is easy to build, and its CRC half is already the rule (no pair above has a Read with the same offset and size and another CRC-32). The bound is the problem:

- the variance includes a whole resource: **3,072,964 bytes** on one side of G3's thread #12 (a 2,637,824-byte stream swapped for another file, plus stream ends), 133,257 in G4 (a first block of a resource), against 10,240 in the pairs calibrated before. A bound of 133,257 plus a margin passes G4 and fails G3; a bound of 3.1 million passes both and also passes a native runtime that does not load any one resource of that size or smaller (and, by the controls above, one that does not load up to 16 runs, which it does today);
- the CRC-32 of a range that the other side did not read, or read in other pieces, cannot be compared without the bytes (the prefix rule of section 10 compares at a part boundary that both sides have; here there is none), so the bytes in the one-sided ranges are never checked against anything. What is checked instead is that everything both sides read is equal, that the result codes are equal, and the counts;
- the variance differs a great deal between the two sessions: G3 (18,000 frames, of which the hunt is the last 3,891) has 21 % of its thread #12's coverage on one side only, G4 (3,000 frames) 1 to 4 % per thread. Whether it grows with the length of a session is a guess, not a measurement (a hunt and a village scene differ in kind, not only in length); if it does, a longer hunt (G5, G7, G8) would need a larger bound;
- a failed load does not look different in a trace from a choice of another resource: both are Reads of a range that the other side lacks.

**Other open differences.** The Reads are not the only reason `--require ipc` fails on G3 and G4. `cross-model.md` section 9.3 lists two more that nothing in N0-36 touches: row 1 (the main thread's ControlArchive input byte, an `fs:` command that is not a Read) and row 2 (the `nwm::UDS` commands, whose entries are still only proposed). Section 9.5 item 2 gives another reading for the loaders' differences, the quest-loading race of `docs/research/system-services.md` (which resource is requested at a moment depends on how many frames have run), and nothing measured here excludes it. So removing the Reads difference alone, by any option below, does not make `--require ipc` pass on these two sessions.

**Options for the decision** (the numbers are above; none was built):

1. *Remove the cause for the comparison*: make the two models draw the same seed. If the seed explanation above is right (a prediction that no run has tested), the choices would then be equal and the pairs exact again except for the places where a stream is cut; a cheap test of it before any re-recording is one run of G4 on each backend with the first clock reading moved to the middle of a second, to see whether thread #3's two one-sided loads and G4's stream ends go away. The reference runner needs a start date finer than a second (so that the first reading is far from a second boundary on both backends; the first reading comes 4.4 ms before a second boundary on recomp and 36 ms after it on jit), the sessions have to be recorded again, and the native runtime in real time has to place its first reading in the same second (N1-25's deterministic mode, which charges the cycles, would). This is not a rule and is outside N0-36 (re-recording, the runner).
2. *A coverage bound*, in the cross and native profiles, per thread and file session, taken from the numbers above with the margin the orchestrator chooses (133,257 for G4 only; 3,072,964 for both), together with the two rules that need no bound and that hold on all 14 saved pairs: a thread and file session that one side reads and the other does not is a difference whatever its size (it holds in every pair above, G3 and G4 included), and a Read with the same offset and size and another CRC-32 or result is a difference (already so). It keeps the check able to see a whole thread that does not read, and not able to see one resource.
3. *Leave `ipc` of G3 and G4 unchecked in the cross and native profiles for their `fs:` reads*: not recommended (the check would not see data read wrong at all).

The `fs coverage:` line gives the number for each future pair (G5, G7, G8, the native runs of G3): if the one-sided bytes stay near 10 KB the runs are of the calibrated kind; if they are hundreds of KB the game chose other resources. Its rows are keyed by the trace's file-session name (`fs:USER/file#k`), unlike the multiset rule, which ignores the session; in all 14 saved pairs both sides number the sessions alike, but a runtime that opens the same files in another order would show each of them as two one-sided sessions, a large number with no real difference, so the line must be read with that in mind; since N0-37 the rules of section 12 are gated on the same key (a read under another session number is a failure there, by design, and the section says what that means). The line also prints the number of separate one-sided ranges, summed over the rows (the table above gives them per thread, e.g. `(2 ranges)`).

## 12. The two blind spots of the `fs:` read rules, closed (N0-37): file sessions read by one side only, and bytes

**Why.** Section 11 listed two holes that the what-if controls of N0-36 found in the rules of D52 and D76, on pairs that pass, nothing to do with the quest sessions: the Reads of a thread can vanish from the candidate and the check still exits 0 when the thread has up to 16 Reads, or (in `native`) when they fuse into up to 16 runs (the movie stream of G1 is one run: surplus 1); and one Read added at another offset passes, because the surplus is a count of Reads (runs) and says nothing of bytes. N0-37 closes both, in `compare_ipc_traces.py` with `--fs-reads-multiset` (so in the `cross` and `native` profiles of `golden.py`; the `same` profile compares the files exactly and is untouched; so is every rule above). Three rules, all computed on the byte ranges the Reads returned (`fs coverage:` of section 11 is the same measurement), per thread:

1. **A file session (`fs:USER/file#k`) that one side reads from and the other does not is a difference whatever its size.** A thread that one side never reads from is the same case, for each of its sessions. No option. It counts a session as read when a Read request was sent to it, whether or not it succeeded (a failed Read is judged by the multiset, whose key has the result). The session is the trace's name for it: the multiset of D52 ignores the number, this rule does not, so a runtime that opens the same files in another order must be compared after its sessions are numbered alike (section 11 warned about it for the `fs coverage:` rows; in all 14 saved pairs both sides number them alike).
2. **`--max-one-sided BYTES` (default 20,480; it was 16,384 until N0-35 part B re-judged it, see below).** The bytes that one side's Reads cover and the other's do not, summed over the thread's file sessions, are at most this on each side.
3. **`--max-detached BYTES` (default 0).** Of those bytes, the ones in a range with no neighbour (the byte just before the range, or the one at its end, is not covered by the other side) are at most this. A detached range is a Read of something the other side never touches, however small; a stream cut at another place is not (it continues a range both sides read).

The defaults of the tool and the profiles' are one pair of numbers: `tools/native/golden.py` has `CROSS_MAX_ONE_SIDED` and `CROSS_MAX_DETACHED` (the cross and the native profile pass them to the tool; a test checks they equal the tool's own defaults). They are not options of `golden.py check`: change the constants, with a decision, not a command line.

**The numbers, and where they come from** (the 14 saved pairs; numbers only; the traces are in `build/`, script `build/n0-37/measure.py`). The 12 pairs that are not G3 or G4 (the jit runs of G1, G2 and G6, and the nine native pairs of N0-33):

| What | Measured over the 12 pairs |
|---|---|
| File sessions that one side reads from and the other does not | 0 in all 14 (G3 and G4 included) |
| Bytes only one side covers, per thread (largest) | 10,240 (the movie stream, #17: jit G1, G2, G6 reference-only; native G1 run 1 candidate-only); at most 8,192 in the other sides (one side has 2,048: the reference side of the fresh native G2 run 1, #17); 8,192 on #12 in the G2 native pairs |
| Ranges that make them up, per pair | 1 (jit, G1 native), 2 (G2 native: #12 and #17); each continues a range the other side reads |

*Why 20,480.* The twelve pairs of G1, G2, G6 and the native runs show at most 10,240 (a stream cut at another place). G4 recorded again at a start date with a fraction (N0-35 part B, D83) shows 18,432 on the movie stream's thread (#17: nine 2,048-byte chunks that the reference reads at the end of the run, the same number as in G4's first recording, so not a matter of the seed); 20,480 is ten chunks, 1.1 times the most seen. ## 14. `timeline_check.py`: the scheduler's timeline against `timing.txt` (N0-39)

(Section 13 is on the parked branch of N0-38, D98.) **What it compares.** The reference runner's `timing.txt` (one
`tick= event= core= late= from=` line per CoreTiming event of a run, after a `#` header) and the native runner's
`MH4N_TRACE_EVENTS` file (`--deterministic`: one `tick= core= late=` line per timer event, and `stretch` and `ended`
lines that are not events and are skipped). The two are streamed (a look-ahead of four events on each side) and the events
are paired in order; a pair is equal when tick, core and lateness are equal. The candidate's lines carry no event name:
the name is the reference's, and is the *kind* the allow file names.

**Differences.** When a pair is not equal, the next three events of both sides decide what it is: if they pair up equal
as they stand it is one event that differs (`differs`); else if they pair up after skipping one reference event it is
`missing`; after skipping one candidate event, `extra`; else `differs`. So one late event is one difference and not a
shifted tail of 143,000. The output is `N of M equal` (M the reference's events), a summary of the differences, and for
each one (the first 20, `--show N`) the events before, at and after it on both sides with their line numbers.

**Exit status.** 0 when every difference is listed in the allow file (or there is none); 1 otherwise; 2 for a malformed
input: a line that is not an event, an unreadable file, a file with no events, an allow file that does not parse.

**The allow file** (`config/native/timeline_allow.txt`, made by the orchestrator): one allowed difference per line,
`ref=<tick>:<core>:<late>:<event> cand=<tick>:<core>:<late>  # reason`, with `-` for the side that has no event (`cand=-`
a missing event, `ref=-` an extra one). A line allows exactly the difference it names, **once**: a difference that occurs
twice needs two lines, and a line whose numbers are one tick off allows nothing. The reason after the `#` is required.
Lines that match no difference are printed as a note and are not an error (the day the residual is fixed, the lines are
to be removed). The four differences of G4 (N1-26) are four lines: the three `UDS::handle_async_event_signals_event`
events, 6 ticks early on core 1 (two of them at the same tick, so two identical lines), and the
`ThreadWakeupCallback_0` of core 0 that follows the first, late by 4 ticks and not 2. *(2026-10-31, N3-32: that day
came. The residual's cause was the deterministic slice, 1,145,774 ticks, 3 short of Azahar's `MAX_SLICE_LENGTH` of
1,145,777, so every thread-safe event was due 6 ticks early; with the slice fixed the four lines matched no difference and
were removed. The file keeps its format comments and lists no difference; a file with comments only allows nothing.)*

**On G4** (the recording of 2026-10-23, the native deterministic runner of the merged tree): 143,290 of 143,294 equal,
4 differences, exit 1 without the allow file and 0 with the four lines; 0.8 s for the comparison. *(2026-10-31, N3-32:
with the slice fixed, 143,294 of 143,294 equal and exit 0 with the emptied allow file; the events of a run before the fix
now exit 1, 4 differences not allowed (the orchestrator's `timeline_check.py` run on N0-39's review run of G4; the fix itself: `docs/research/det-120fps.md`).)* **What it cannot see**:
see `golden.md`, *`check --timeline`*, on the slice caps `--slice-us 4275`, `4273` and `3000`, which leave G4's events
