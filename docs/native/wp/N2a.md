# N2a · Native renderer from captures

The renderer is built and checked against N0's GPU captures (`MGPU`, N0-05 and N0-22), without the runtime, so this phase runs in parallel with N1. It implements `mh4n::gpu::Gpu` (`native/include/mh4n/gpu.h`, N1-01): the same interface the null GPU of N1-17 implements, so N2b only has to swap one for the other. The phase's exit is in [`../ROADMAP.md`](../ROADMAP.md#5-phases); the workflow is [`../AGENTS.md`](../AGENTS.md); the rules for code in `native/` are at the top of [`N1.md`](N1.md).

N2-39 is on no path.

**The oracle.** Every check in this phase is a capture replay (N2-02):
- per GX command, the memory the GPU wrote against the capture's `GPU_PAGES`;
- per command list, the register writes against `PICA_REG`;
- per frame, the displayed screens against the reference PPMs from Azahar's software renderer at 1x, with the thresholds of [`../ROADMAP.md`](../ROADMAP.md) §6: PSNR ≥ 40 dB, and no 16×16 block with a mean error above 8/255.

Azahar draws no gas at all (its shader generator logs "Unimplemented gas mode", and its software renderer handles only plain fog), so frames that use gas are left out of the image checks (`--skip-gas-frames`) and checked later against a real 3DS ([`LATER.md`](LATER.md), `3ds`).

**Where to run it:** in the cloud on lavapipe (a CPU Vulkan driver: slow, but exact enough for the image thresholds); timings only on the reference PC and the M2.

**Captures** are game data. They are `build/golden/<S>/gpu-<start>.mgpu` (N0-09, N0-10), in the session that recorded them or staged from the maintainer's PC (AGENTS §6). A session that runs these checks needs the dump staged and the captures recorded or staged; G3 and G4's need the save to record. "The G1–G4 captures" means every GPU capture of G1, G2, G3 and G4.

**Where the code goes.** Each part of the renderer is its own module under `native/src/gpu/`: `gx/` (N2-03), `pica/` (N2-04), `vertex/` (N2-05), `shader/` (N2-06), `backend/` (split by directory, one owner each, so the slices run in parallel: `plume/` N2-25 (the vendored copy itself is `native/third_party/rhi/`, N2-25 then N2-29), the two interface headers and `core/` N2-26, `targets/` N2-27, `sync/` and `readback/` N2-28, `state/` N2-13), `queue/` (N2-22), `fbops/` (N2-13), `texture/` (N2-14), `cpuvertex/` (the CPU path of the draws Azahar does not accelerate, N2-36 then N2-37), `fragment/` (its core N2-33, the generator N2-08, with one directory per feature: `sampling/`, `lighting/`, `fog/`, `proctex/`, `shadow/`), `native/` (`pipeline_key.h` and the composition's slots N2-33, the composition registered as `--gpu native` N2-08), `surface/` (N2-15), `pipeline/` (N2-16), `hd/` (N2-18). GPUs, GPU wrappers, capture-player options, checks and report columns register themselves (N1-01's registry), so no WP edits the capture player after N2-02. A tool's logic is a module under `native/src/` (`gpu_capture/`, `vkprobe/`, `hdpack/`), so tests can link it; its `native/tools/` directory holds only `main`.

### N2-24 · Vulkan probe (`mh4n_vkprobe`)
- **Size / agent:** M · native-worker
- **Depends on:** N1-01 · **Needs:** ci
- **Goal:** build, before the PICA census exists, the tool the RHI spike (N2-01) measures with: `mh4n_vkprobe` reports which of the Vulkan features MH4U's rendering needs a device offers, from a live device or from `vulkaninfo --json`, and the CI artifacts carry it, so the maintainer can run it on the PC and the Mac while the census waits for his save.
- **Read first:** D4; `docs/research/metal.md`; Azahar's `src/video_core/renderer_vulkan/vk_instance.cpp` (the features and extensions its Vulkan renderer checks for, and its fallbacks); `docs/native/ENV.md` (lavapipe); `.github/workflows/native.yml` (the packaging and smoke steps of `native-windows`, N1-22b) and `docs/native/CI.md`.
- **Files (allowlist):** `native/src/vkprobe/**` (new: the probe, the report and the JSON reader), `native/tools/vkprobe/**` (new: `main`), `native/tests/vkprobe_test.cpp`, `native/third_party/vulkan/**` (new: the vendored header, see Spec), `docs/research/vkprobe.md` (new: the maintainer's procedure), `.github/workflows/native.yml` (a lavapipe step in `native`, the probe in the Windows artifact, a macOS artifact), `docs/native/CI.md` (the sentences about the artifacts).
- **Spec:**
  - **`mh4n_vkprobe`** prints, for each Vulkan device, the features MH4U's rendering needs, each with its fallback when absent:
    - logic ops (`logicOp`);
    - fragment shader interlock (pixel and sample), and storage image writes from fragment shaders;
    - geometry shaders; fragment shader barycentrics (the quaternion fix-up without geometry shaders);
    - triangle fans (absent under the portability subset, so on MoltenVK); 8-bit indices (`VK_EXT_index_type_uint8`);
    - custom border colours; `shaderClipDistance`; `VK_EXT_shader_stencil_export`;
    - `VK_EXT_rasterization_order_attachment_access`;
    - depth-stencil formats (`D24_UNORM_S8_UINT` is missing on AMD; the fallback is `D32_SFLOAT_S8_UINT`);
    - BC7;
    - dynamic rendering; `VK_EXT_graphics_pipeline_library`; push descriptors; timeline semaphores; `VK_EXT_extended_dynamic_state` 1 to 3;
    - `VK_KHR_present_id` and `VK_KHR_present_wait` (with `presentId` and `presentWait`), for a swapchain: without them the time a frame is shown cannot be measured (D57, N2b-24); the probe reports them as the device offers them, and says it cannot tell a swapchain's support from a device's when it has no surface.
  - **Output:** a text table (device, driver, API version, one line per feature: `yes`, `no (fallback: …)` or `unknown`), and `--json` for the same data as one JSON document per device, so `rhi-spike.md` can quote it.
  - **`mh4n_vkprobe --from-json FILE`** reads `vulkaninfo --json` output (and the report's own `--json`) instead of a live device, so a machine without our build can be evaluated. The reader and the report need no Vulkan at all and are always built.
  - **Live probe without an SDK:** the program loads the Vulkan loader at run time (`vulkan-1.dll`, `libvulkan.so.1`, `libvulkan.1.dylib`) and takes the declarations from a vendored `vulkan_core.h` (Khronos Vulkan-Headers, Apache-2.0 OR MIT: one file pinned to a release, with its licence, listed in `native/THIRD_PARTY.md` by the orchestrator), so the three CI jobs build it with no Vulkan package and a PC without the SDK can run it. No loader, or no device: the live probe says so and exits 3, and `--from-json` still works.
  - **`docs/research/vkprobe.md`:** the procedure for the maintainer: where the CI artifact is (`mh4n-runner-windows`, `mh4n-vkprobe-macos`) and the command for each machine (`mh4n_vkprobe --json > vkprobe-<machine>.json`, plus `vulkaninfo --json` where he has it), what to send back, and until he does, how to use reports for the same GPU, OS and a recent driver from https://vulkan.gpuinfo.org (say which).
  - **CI:** in `native`, a step runs `build/native/bin/mh4n_vkprobe` (mesa-vulkan-drivers is installed there, so lavapipe is a device) and fails unless the table names a `llvmpipe` device; in `native-windows`, the packaging step adds `mh4n_vkprobe.exe` with the same DLL copying and smoke check as the other tools (`usage: mh4n_vkprobe` for `--help`); in `native-macos`, an upload step publishes `mh4n_vkprobe` as the artifact `mh4n-vkprobe-macos` (30 days, not on pull requests; the file is an unsigned arm64 executable: say in the doc how to run one that a browser download quarantined).
- **Done when:**
  - *(CI)* the three native jobs build it; `native` prints the lavapipe device's table; `native-windows` runs the packaged `mh4n_vkprobe.exe --help` with no llvm-mingw on the `PATH`; the two artifacts exist;
  - `ctest` runs `vkprobe_test`: `--from-json` reads a synthetic `vulkaninfo` file (made by the test, not a real device's) and prints the expected `yes`/`no (fallback)`/`unknown` for each feature, including the missing-extension and the portability-subset (no triangle fans) cases, and rejects a truncated file with a clear error;
  - `python3 tools/native/check_native_deps.py` passes (nothing here uses Azahar).
- **Traps:** a real `vulkaninfo --json` differs between SDK versions (the layout of `capabilities` and `extensions`): read the keys by name and treat an absent feature as `unknown`, not `no`. Never claim a feature from a name the driver did not report. `vulkan_core.h` is large; vendor it once and do not edit it.
- **Out of scope:** the spike's analysis and recommendation (N2-01); the RHI (N2-25 to N2-29); the probe's `--rhi` report (N2-30).

### N2-02 · Capture player and comparison harness
- **Size / agent:** M · native-worker-high
- **Depends on:** N0-22, N1-01 · **Needs:** dump-check
- **Goal:** `mh4n_capture_player` replays an `MGPU` capture into any `mh4n::gpu::Gpu` implementation and checks it against the capture: memory per command, registers per command list, images per frame, with the thresholds, and times every frame. Later WPs plug their GPUs, options, checks and report columns into it without editing it.
- **Read first:** `docs/native/mgpu-format.md` and `tools/native/gcap.py` (N0-22); `native/include/mh4n/gpu.h`, `registry.h` and `options.h`; in Azahar: `src/video_core/renderer_software/renderer_software.cpp` (how a displayed screen is made from the framebuffer: formats, rotation).
- **Files (allowlist):** `native/tools/capture_player/**` (new), `native/src/gpu_capture/**` (the reader, the capture host and the check interface, shared with tests), `native/include/mh4n/gpu_debug.h` (new), `native/tests/capture_player_test.cpp`, `docs/native/capture-player.md` (new).
- **Spec:**
  - **Reading:** a C++ reader for `MGPU` that mirrors `gcap.py`, and a `CaptureHost` (`gpu::Host`) over a physical memory image of FCRAM and VRAM built from `MEM` records; its `Post` runs the work at once.
  - **`mh4n/gpu_debug.h`:** what a `Gpu` can also implement for the player (found with `dynamic_cast`):
    - `LoadInitState(const InitState&)`: the GPU state at the start of the capture, from the `INIT` record's blocks (registers, shader setups and uniforms, default attributes, the LUTs, the immediate-mode and geometry-pipeline state);
    - the register writes it decoded, in `PICA_REG` form, for `--check registers`;
    - its colour buffers written back to guest memory, for the image checks;
    - `TakeFrameCounters()`: named counters for the frame (draws through the ubershader, HD textures ready, …), printed as extra columns.
  - **Registry:** GPUs register a `gpu::GpuFactory` by name (`--gpu NAME`); GPU wrappers register a `gpu::GpuWrapper` (`std::function<std::unique_ptr<Gpu>(std::unique_ptr<Gpu>, Host&, const Options&)>`, declared in `gpu_debug.h`) by name, and the player applies each wrapper whose same-named flag is set (N2-22's `--queue`); checks register a `CaptureCheck` (`--check NAME`), which sees every record and every frame and adds its own columns; options register in the `capture-player` scope. So a WP adds one of these from its own module.
  - **Replay:** records in order. `INIT` goes to `LoadInitState` before the first `GX`; `CPU_PAGES` go into memory; `GX`, `MMIO`, `SWAP` and `FILL` go to the `Gpu`; `FLUSH` kinds 1, 3 and 4 go to `FlushRegion`, kind 2 to `InvalidateRegion`. `IRQ` records of PDC0 and PDC1 are VBlanks: the player calls `Gpu::VBlank(screen)` there. The other `IRQ` records are what the `Gpu` should signal, compared in order (ids only: the GSP ignores the delays, D25).
  - **Modes:**
    - `--isolated`: `GPU_PAGES` are applied after each command is checked, so every command starts from the reference inputs;
    - `--chained` (the default): they are only compared, so errors build up as they would in the game;
    - `--judge KINDS` (default `fill,transfer,copy,dma,cmdlist,frames`): what is judged. Commands of other kinds are still sent to the `Gpu`, then their `GPU_PAGES` are applied in place of its output and they are reported as skipped; without `frames`, the image checks are reported but not judged. So a GPU that does only part of the work can be checked on that part.
  - **Checks:**
    - after each `GX`, the pages the `Gpu` wrote against `GPU_PAGES`: bit-exact for fills and copies; for draws, through the image thresholds applied to the colour buffer;
    - `--check registers`: the decoded register writes against the `PICA_REG` records;
    - at each `FRAME`, the displayed top and bottom screens (from the `SWAP` information and memory) against the PPMs: PSNR ≥ 40 dB and the 16×16 block rule, both reported per frame;
    - `--skip-gas-frames`: frames whose command lists set fog mode 7 are reported but not judged.
  - **Output:** a table per frame (PSNR, worst block, pass or fail, CPU time spent in the `Gpu`, GPU time from timestamps when the backend has them, the counters and the checks' columns); `--dump-frames DIR` writes the native images and difference images as PPM; exit status 0 when everything passes.
  - **Two GPUs ship with the harness**, to test it: `replay` writes the `GPU_PAGES` itself and must pass; `none` does nothing and must fail at the first draw.
- **Done when:**
  - ctest passes with synthetic captures (made by a C++ writer in the test): `replay` passes; `none` fails at the expected record, and passes with `--judge none`; a 16×16 block uniformly off by 10/255 fails the block rule while PSNR stays above 40 dB; one fully wrong pixel passes both; the `INIT` state reaches the `Gpu` before the first command; each `FLUSH` kind reaches the right call; PDC records become `VBlank` calls; a GPU, a wrapper, a check, an option and a counter registered from another directory are found and shown;
  - (with the dump) `--gpu replay` passes on G1's capture, and the timing table prints.
- **Traps:** -
- **As built (N2-02), for the WPs that plug into the player** (the contracts are `native/include/mh4n/gpu_debug.h` and `native/src/gpu_capture/check.h`; `docs/native/capture-player.md` describes the tool):
  - The four members listed above are `LoadInitState`, `TakeRegisterWrites`, `WriteBackColorBuffers` and `TakeFrameCounters`; `GpuDebug` also has `TakeFrameGpuTimeNs`. A wrapper (N2-22) must implement `GpuDebug` and forward it to the `Gpu` it wraps. A WP that adds a GPU, wrapper or check lists `mh4n_gpu_capture` in its `DEPENDS` and includes `gpu_capture/check.h`; nothing in the player is edited to register one.
  - N2-04's `--check registers` needs only `GpuDebug::TakeRegisterWrites` (an empty optional means "not decoded").
  - Open assumptions, to confirm on the first real capture (dump check): command-list judging on RGB colour buffers, Azahar's off-by-one screen column, the frame and PPM numbering, and the timing columns.
- **Follow-up N2-03b (the capture player):** `GPU_PAGES` of a command that signals an interrupt holds the page of the GSP's shared memory that the GSP service changes inside `GPU::Execute` (the interrupt relay queue; the reference delivers the interrupt at once, D25), which no `Gpu` writes. The player does not judge such a page as the `Gpu`'s output when the capture's change of it, against the capture's memory before the command, is exactly the command's own non-VBlank interrupts pushed into one of the four queues (Azahar's `queue_interrupt`) and the `Gpu` did not touch it; it applies the page to the `Gpu`'s memory and counts it in the summary. It also prints, for a failing fill, transfer, copy or DMA, the decoded command, the output region, the pages and the offsets of differing bytes per page (never bytes), and lists the selected kinds the capture does not exercise (`docs/native/capture-player.md`). Every exact-judged `Gpu` to come (N2-15 on) relies on the same rule; a `Gpu` or wrapper must never write that page.
- **Out of scope:** any real GPU work (N2-03 onwards).

### N2-03 · GX engine
- **Size / agent:** M · native-worker
- **Depends on:** N2-02 · **Needs:** dump-check, save
- **Goal:** memory fill, display transfer (formats, scaling, tiling, flips), texture copy and DMA, bit-identical to Azahar's software implementation, on the CPU. This is the reference the surface cache's GPU versions (N2-15) are checked against.
- **Read first:** in Azahar: `src/video_core/gpu.cpp` (`Execute`, `MemoryFill`, `MemoryTransfer`), `src/video_core/renderer_software/sw_blitter.cpp` (`DisplayTransfer`, `TextureCopy`, `MemoryFill`), `src/video_core/pica/regs_external.h`; 3dbrew *GPU/External Registers*.
- **Files (allowlist):** `native/src/gpu/gx/**`, `native/tests/gpu_gx_test.cpp`.
- **Spec:**
  - The four operations from the GX commands, with every input and output format and flag the registers allow: the 2x downscales, tiled ↔ linear, the vertical flip, the texture-copy gaps.
  - The interrupts each one signals, with Azahar's delays.
  - Port `sw_blitter.cpp`'s logic (D6, with provenance).
  - Registers `--gpu cpu-gx` with the capture player: this engine with nothing for command lists.
- **Done when:**
  - ctest passes: each format pair and flag on synthetic images, against expected bytes worked out from the algorithm;
  - (with the dump) every fill, transfer and copy in the G1–G4 captures matches `GPU_PAGES` bit for bit: `--gpu cpu-gx --isolated --judge fill,transfer,copy,dma` passes.
- **Traps:** -
- **As built (N2-03):** `--gpu cpu-gx` is registered by `native/src/gpu/gx`. It follows Azahar's addresses for the register windows (LCD registers at `0x1ED02000`, GPU registers at `0x1EF00000` and `0x1EF01000`: the GSP base `0x1EB00000` plus the offsets of `WriteHWRegs`). Where Azahar reads or writes out of range or meets a pixel format that does not exist, the engine reads zeros, skips the write and logs, instead of crashing the host. It does nothing for command lists, the display (a buffer swap only updates the registers) or the cache. `GxEngine` is a `Gpu`, not a `GpuDebug`: a capture's INIT record (the GPU and LCD register blocks) is not loaded into it, so its registers start at zero and `--gpu cpu-gx` is only valid for captures driven by GX commands whose registers the capture itself sets (`pica-only` does load them).
- **Follow-up N2-03b:** the six `DISPLAY_TRANSFER` failures of G1 and G2 were not in the engine: `blitter.cpp` and `engine.cpp` were compared line by line with Azahar's `sw_blitter.cpp`, `gpu.cpp`, `regs_external.h` and `color.h` and nothing differs; the failing page is the GSP's relay queue (see N2-02's follow-up). Fill, copy and DMA are not exercised by the G1 and G2 captures: they are not verified. `GxEngine::Dma` for ranges the host cannot translate is still D41's open follow-up.

### N2-04 · PICA command processor
- **Size / agent:** M · native-worker-high
- **Depends on:** N2-02 · **Needs:** dump-check, save
- **Goal:** the command-list decoder and register file, with every side effect of a register write, producing draw calls; its register writes are identical to Azahar's.
- **Read first:** in Azahar: `src/video_core/pica/pica_core.cpp` (command lists, the internal register writes and their side effects), `regs_internal.h` and the other `regs_*.h`, `shader_setup.cpp` (program and uniform uploads), `vertex_loader.cpp` (only to see where draws start); 3dbrew *GPU/Internal Registers* and *GPU/Commands*.
- **Files (allowlist):** `native/src/gpu/pica/**`, `native/tests/gpu_pica_test.cpp`.
- **Spec:**
  - **Decoding:** the header word (register id, parameter mask, extra parameter count, consecutive flag), byte masks, the alignment rule between commands.
  - **Side effects of writes,** as Azahar:
    - the vertex and geometry shader program and swizzle uploads (with their offset registers);
    - float uniforms (f24 in three-word mode, f32 in four-word mode), integer and boolean uniforms;
    - default and fixed attributes;
    - the lighting, fog and procedural-texture LUT uploads;
    - jumps between command lists (the command-buffer address, size and trigger registers);
    - the draw triggers (draw arrays and draw elements) and immediate-mode vertex submission;
    - the geometry-pipeline setup.
  - **The start state:** `LoadInitState` (N2-02's `gpu_debug.h`) fills the register file, shader setups, LUTs and attributes from a capture's `INIT` record.
  - **Output:** a `DrawCall` per draw: the register state and shader setups it needs, and where its vertices come from. A `Backend` interface receives them; this WP comes with a recording backend for tests. Decoded writes are reported through `gpu_debug.h`, and the module registers `--gpu pica-only` for `--check registers`.
- **Done when:**
  - ctest passes: synthetic command lists for each side effect, and a start state loaded from a synthetic `INIT`;
  - (with the dump) `--gpu pica-only --isolated --judge none --check registers` passes on every command list of the G1–G4 captures.
- **Traps:** -
- **As built (N2-04), for N2-05, N2-06, N2-08, N2-16 and N2-22** (the contracts live in the module, included as `gpu/pica/backend.h` and `gpu/pica/state.h`, with `DEPENDS mh4n_gpu_pica`; they are not in `native/include/mh4n`):
  - `Backend::Draw(const DrawCall&)`; a `DrawCall` is `{kind (Arrays, Indexed or Immediate), sequence, vertex_base_address (physical), num_vertices, vertex_offset, index_offset, index_u16, geometry_reconfigured, const PicaState* state}` and carries no vertex data: N2-05 loads vertices from `vertex_base_address` and the loader registers. The `state` pointer is valid only during `Draw`: a backend on another thread (N2-22) copies the `PicaState` (about 105 KB) or the processor runs on the renderer thread. The processor clears the dirty flags (registers, the lighting, fog and procedural-texture tables, the program, swizzle and uniforms of both setups) after `Draw` returns, so they mean "changed since the previous draw returned".
  - Immediate mode emits one `Immediate` draw per full vertex, with `state->immediate.input_vertex`. The geometry pipeline is reconfigured from the registers at every `Arrays` or `Indexed` draw and at the first immediate vertex after a write to `0x232`; its cursors (buffer index, vertex counts, attribute buffer) and the geometry shader's `b15` rule are left to whoever runs the vertex shaders (N2-06). The processor keeps no primitive-assembler state (Azahar's hardware renderers do not either).
  - `PICA_REG` entries are produced per register word written (a repeated-register command gives one entry per word, with the command's raw value; out-of-range ids are not recorded), as `mgpu-format.md` §3.5 describes. `--gpu pica-only` does only `SubmitCmdList` and the MMIO triggers (use it with `--judge none`); it counts draws as frame counters (`pica_draws`, `pica_immediate_draws`, `pica_cmdlists`).
  - Mirrored Azahar quirks, on purpose: handlers get the unmasked word while the register gets the masked one; a refused program or swizzle batch drops the whole batch; the extra words of a command come from the list as it is after the first write; a uniform batch gives up at the first out-of-range index; unit 3 mirrors the vertex unit only when `gs_unit_exclusive_configuration` and `use_gs` are 0. Deviations where Azahar crashes or reads out of bounds: a lighting LUT type of 24 or more is dropped; a fixed-attribute index above `0xF` empties the queue; a jump or list at an unmapped address ends the list; geometry-shader mode 3 and inconsistent register sets are logged and treated as no geometry shader.
  - Assumptions to confirm on the first real capture (dump check): the recorder lists one `PICA_REG` entry per register word, in order; like Azahar, a list whose last command ends on an odd word makes the loop read one more (value, header) pair from the 8 bytes after the list (real lists end with the finalize write, which stops the loop first).
- **Out of scope:** drawing (later WPs).

### N2-05 · Vertex loading
- **Size / agent:** M · native-worker
- **Depends on:** N2-04, N2-01 · **Needs:** dump-check, save
- **Goal:** vertex data from the PICA's vertex arrays into host vertex buffers, exactly as Azahar's `VertexLoader` feeds its vertex shader, in shapes every backend can draw.
- **Read first:** in Azahar: `src/video_core/pica/vertex_loader.cpp`, `src/video_core/pica/regs_pipeline.h`, how its hardware renderers set up vertex input (`src/video_core/rasterizer_accelerated.cpp`) and its vertex formats and their fallback (`src/video_core/renderer_vulkan/vk_instance.cpp:72-97, 350-395`); `docs/research/rhi-spike.md` 2 (N2, N4, N5, X3, X7), 3.3, 4, 9.3 and 9.4 items 10 and 11.
- **Files (allowlist):** `native/src/gpu/vertex/**`, `native/tests/gpu_vertex_test.cpp`.
- **Spec:**
  - The attribute loaders: up to 12 attributes in up to 12 buffers, byte, unsigned byte, short and float components, 1–4 per attribute, strides, the default and fixed attributes, index buffers of 8 and 16 bits, immediate mode.
  - **What the device allows** comes in as `VertexCaps` (a struct of this module: `triangle_fans`, `index_uint8`, `apple`, `stride_alignment`, `primitive_restart_always_on`), which the caller fills from the backend's `Capabilities` (N2-26; `--gpu native` does it, N2-08), so this WP needs no backend and no device.
  - **Shapes** (`rhi-spike.md` 3.3, 4, 9.4 item 11): none of the three Vulkan devices lacks fans or 8-bit indices (MoltenVK and KosmicKrisp emulate fans, MoltenVK converts 8-bit indices with a compute pass at draw time); native Metal lacks both. The rule: triangle fans become indexed triangle lists when `triangle_fans` is off **or `apple` is set** (the emulation costs render-pass restarts, plume_vulkan.cpp:4173-4180); 8-bit indices become 16-bit when `index_uint8` is off or `apple` is set (Azahar blacklists them on MoltenVK, 5.1).
  - **Strides** (N5, 9.4 item 10): a buffer whose stride is not a multiple of `stride_alignment` (`minVertexInputBindingStrideAlignment` under the portability subset: 1 on Apple8, 4 below Apple5; 1 on a full device) is repacked on the CPU to the next multiple.
  - **Attribute formats** (X3): plume has no `SSCALED`/`USCALED` formats (6.1, X3), so byte and short attributes always go as integer formats with a conversion the vertex shader applies (Azahar's own fallback), the 3-component cases as Azahar's `vk_instance.cpp` aliases them (ported with provenance); the vertex-input description says, per attribute, the format and whether the shader converts (N2-06 reads it).
  - **Primitive restart** (X7, 9.4 item 10: treated as always on on Apple; MoltenVK always restarts, KosmicKrisp's value is `inference`, N2-26): where `primitive_restart_always_on`, a 16-bit index list that contains 0xFFFF is widened to 32-bit for that draw, so no index reads as a restart (the widening is the planner's choice of route: X7 only says the hazard exists); whether the PICA submits such indices is `unverified`, so each widened draw is counted (`vertex_restart_widened`, for N2-08's counters).
  - Output: host buffers and a vertex-input description for the backend, in a form that doesn't depend on the RHI's types (offsets, formats, strides).
  - A CPU reference port of Azahar's `VertexLoader` (in the tests only, with provenance) checks the output.
- **Done when:**
  - ctest passes: synthetic arrays for every format, both index sizes, fans converted;
  - (with the dump) for every draw of the G1–G4 captures, the first 64 vertices loaded equal the CPU reference's.
- **Traps:** -
- **As built (N2-05), for N2-06, N2-08 and N2-26** (the module is `native/src/gpu/vertex/`, `mh4n_gpu_vertex`, `DEPENDS mh4n_gpu_pica`; its API and the layout of the vertex-input description are the header comment of `vertex_loader.h`; it uses no RHI type and nothing in `native/include/mh4n`):
  - **Where it follows the interpreter, not the hardware renderers:** a default-flagged attribute wins over a loader that provides it; the later attribute wins on a shared register; only the attributes up to the vertex shader's last input are described. One deliberate difference: a loader with `byte_count` 0 is skipped, as the hardware renderers do (the interpreter would read vertex 0's bytes for every vertex).
  - **The w lane of an aliased attribute:** 3-component byte, unsigned byte and short attributes are always aliased to the 4-component integer format with `alias_w` (there is no device query). The vertex shader must write w = 1.0 on that lane, as Azahar's interpreter does (it is N2-06's oracle); Azahar's GLSL generator writes 0 there (`ZeroW`) and is not to be copied.
  - **Restart widening:** besides the 16-bit lists the spec names, an 8-bit list that stays 8-bit and holds 0xFF is widened to 16-bit under `primitive_restart_always_on`. Both widenings count in `vertex_restart_widened` (`kCounterRestartWidened`); `VertexLoader::counters()` also has `fans_converted`, `draws_loaded` and `draws_dropped`.
  - **Dropped draws:** a draw is dropped with a status (`Unmapped` for a range outside guest memory, `NoVertices`, `TooLarge` for an Arrays draw of more than 1<<24 vertices) and counted in `draws_dropped`. The module reads the whole index range of an indexed draw, like the hardware renderers.
  - **Immediate mode** returns only the constant buffer, with the vertex's attributes already mapped to the input registers. Nothing yet assembles successive immediate vertices into primitives: that is for whoever runs the shaders (N2-04's as-built note says the same).
  - **For N2-26's `ToPlume`:** an aliased attribute that is last in a vertex can have offset + size > stride (3 shorts in a 6-byte vertex read as 8 bytes). The buffer carries 16 tail bytes, but a device with `vertexAttributeAccessBeyondStride` false (the portability subset, Apple) must not rely on it.
  - **The dump check, for the PC** (the last *Done when* line; the row stays `dump-check pending`): `MH4N_VERTEX_CAPTURES=<.mgpu files or directories, separated by ':' (';' on Windows)> ctest --test-dir build/native -R gpu_vertex -V`. Each capture is replayed once through the capture player and the PICA processor, with all four device profiles (full; no fans, no 8-bit indices, stride 4; Apple; restart and stride 3) loading at each draw. A pass is exit 0 with `vertex dump check: N captures x 4 device profiles; draws seen …, draws checked … (above 0), vertices compared …, registers compared …, mismatches 0, index mismatches 0, module dropped a draw the reference can read 0, reference could not read a vertex the module loaded 0`; it prints counts only. Without the variable the case skips with a message.
- **Out of scope:** the vertex shader (N2-06).

- **Size / agent:** L · native-worker-high
- **Depends on:** N2-04, N2-26 · **Needs:** dump-check, save
- **Goal:** PICA vertex shaders (and geometry shaders: the census of N0-13 shows them, in Point mode, in 39 to 90 percent of the draws of its four scenes and about 1 percent of the vertices) translated to SPIR-V with the PICA's float rules, compiled when first used and cached by program hash.
- **Read first:** D27; in Azahar: `src/video_core/shader/generator/glsl_shader_decompiler.cpp` (the PICA → GLSL decompiler; `sanitize_mul` near line 828) and `glsl_shader_gen.cpp`, `src/video_core/shader/shader_interpreter.cpp` (the reference semantics; MAX and MIN near line 265), `src/video_core/pica_types.h` (f24, and the multiply rule near line 93); 3dbrew *Shader Instruction Set*; `docs/research/pica-census.md` (geometry shaders).
- **Files (allowlist):** `native/src/gpu/shader/**`, `native/third_party/glslang/**`, `native/tests/gpu_shader_test.cpp`.
- **Spec:**
  - Port Azahar's decompiler (D27), with provenance; compile to SPIR-V with glslang, linked as a library. The cache key is the program and swizzle hashes plus the output map (and the per-attribute conversions below).
  - The attributes N2-05 passes as integer formats (its vertex-input description says which) are converted to float in the shader, as Azahar's generator does for its integer fallback (`rhi-spike.md` X3: the vendored plume has no scaled formats).
  - **The PICA's float rules** where they differ from IEEE: `MUL`, `DP3`, `DP4`, `DPH` and `MAD` give +0 for 0 × ±infinity, while a NaN factor stays NaN; `MAX` and `MIN` order as the hardware does (`src1 > src2 ? src1 : src2` for MAX, and the matching rule for MIN). f24 precision is approximated with f32, as Azahar does.
  - **Oracle:** a CPU port of Azahar's shader interpreter (in the tests only). For each captured draw, run the translated shader on lavapipe through the backend's core (N2-26: a vertex-stage pipeline from SPIR-V in a pass with no attachments, the outputs written to a storage buffer and read back with `ReadBuffer`; the shader's bindings follow `rhi.h`'s binding sets) for the draw's uniforms and its first 64 vertices (writing the outputs to a storage buffer), and compare with the interpreter's: equal when both are NaN, or the same infinity, or `|a − b| ≤ 2^-16 × max(1, |a|, |b|)`.
  - **Addendum 2026-10-24 (D5)**, a contract for the fragment stage (`docs/native/gpu-fragment-design.md` 4.1 and 8 (h)), not new scope: (1) **the varyings:** the translated vertex stage writes the 7 varyings the fragment shader reads, `primary_color`, `texcoord0`, `texcoord1`, `texcoord2`, `texcoord0_w`, `normquat` and `view`, at the locations of Azahar's `DefineInterface` (`src/video_core/shader/generator/glsl_fs_shader_gen.cpp:1267`; the vertex side of the same interface is Azahar's `glsl_shader_gen.cpp`), each component from the output register and component the program's output map assigns to its semantic, as Azahar's vertex generator writes them at the pinned commit `5f3306d` (`src/video_core/shader/generator/glsl_shader_gen.cpp:219-277, 291-293`): the output registers start at (0, 0, 0, 1) before the program runs, a semantic the output map leaves unassigned reads 1.0, and `primary_color` is `min(abs(colour), vec4(1.0))`; (2) **the output map:** the output-attribute map that is already part of the cache key is returned to the caller with the compiled stage (an accessor in this module's public header; name it in the report), so the composition (N2-33, N2-08) and `lighting/`'s generator of the fixed geometry shader (N2-09) build from it without decoding the program again. The oracle and the *Done when* stand (your oracle reads the stage's outputs from a storage buffer in a no-attachment pass: that form stays the oracle's; the varyings are the product's, and N2-08's *Done when* checks the varyings of a translated stage through the fragment stage). (3) **What is not this WP's:** the geometry-shader draws are drawn on the CPU, as Azahar draws them (`docs/research/rhi-spike.md` 5.4), by N2-36 and N2-37, and so are the geometry pipeline's cursors, the geometry shader's `b15` rule and the assembly of immediate-mode vertices, which N2-04's and N2-05's *As built* notes leave to "whoever runs the shaders": that is N2-36 and N2-37, not this WP. The Goal's clause about translating geometry shaders is therefore **optional**: no package consumes a SPIR-V translation of a PICA geometry program and the *Done when* names vertex programs only, so this WP may stop at the vertex programs; geometry-program code already written may stay if its tests pass.
- **Done when:**
  - ctest passes: each instruction against the interpreter on synthetic programs, flow control included (`IFU`, `IFC`, `LOOP`, `CALL*`, `BREAKC`, `JMP*`), and the special cases (0 × inf, NaN operands, MAX/MIN with NaN);
  - (with the dump) every vertex program in the G1–G4 captures passes the oracle.
- **Traps:** compiling with glslang at run time costs milliseconds: the pipeline cache (N2-16) has to hide it.
- **Out of scope:** the fragment pipeline (N2-07 onwards).
- **As built (N2-06), for N2-08, N2-09 and N2-16** (module `native/src/gpu/shader/`, `mh4n_gpu_shader`, `DEPENDS mh4n_gpu_pica mh4n_gpu_vertex`; glslang 16.6.0 vendored in `native/third_party/glslang/` as the static library `mh4n_glslang`; the API is the header comment of `vertex_shader.h` and names no RHI type):
  - **Key and cache.** `MakeVertexShaderConfig(state, &loaded_draw, options)` is the cache key: the program and swizzle hashes of the loaded words and their sizes, the entry point, the output mask, the OUTMAP registers (0x4F and following), the per-register conversion and `alias_w` of N2-05's description, and the options. `VertexShaderCache::Get(state.vs, key)` returns a `TranslatedVertexShader` (SPIR-V, output map, semantic map, used inputs, notes, `differs_from_interpreter`) or an error message; failures are cached; the cache is thread-safe, and its lock is dropped while translating, so two threads that miss on one key both translate and the second result is dropped. Uniforms are not part of the key. A typical shader (17 instructions) compiles with glslang in 2.7 to 3.2 ms (RelWithDebInfo); 3,000 straight-line instructions in 0.04 s.
  - **Interface to the pipeline.** Set 0: binding 0 `PicaUniformData` (1,616 bytes), binding 1 `VertexUniformData` (32 bytes), both std140 (bindings 0 and 1, and 15 for the test hook, are the vertex stage's: N2-08's fragment buffer takes another binding or set; Azahar's is 2). Inputs at `location = register`, typed `vec4`, `ivec4` or `uvec4` by the conversion of N2-05's description. Outputs at locations 1 to 7 (`primary_color`, `texcoord0` to `texcoord2`, `texcoord0_w`, `normquat`, `view`, Azahar's `Attributes` enumeration), `gl_Position`, and `gl_ClipDistance[2]` with `use_clip_planes` (default true, because the core enables `shaderClipDistance`: N2-08 sets it from the device). `ConfigOptions::geometry_stage` emits the outputs as `vs_out_attr<n>` at locations 0 to n-1 for the fixed geometry shader (N2-09). The output map is exposed as `TranslatedVertexShader::{num_outputs, output_map, semantic_map}` (this meets the design document's 8 (h)); a PointList pipeline needs `gl_PointSize` written (VUID-08773): only the test hook writes it, the production stage targets triangles.
  - **Where it differs from Azahar, on purpose.** A semantic that no output attribute maps is 1.0 in every lane (Azahar's `semantic()`; the design document's 8 (h) said zero, which was wrong); the lanes of a mapped attribute that the program never writes start at (0, 0, 0, 1). The w lane of an `alias_w` input is 1.0 (the interpreter's, N2-05's As built; Azahar's generator writes 0). BREAK and BREAKC are translated (Azahar's decompiler rejects them; the Done-when names BREAKC). LOOP follows the interpreter (aL gets the increment after a break; a loop that ends inside another loop sets aL to its own initial y: the interpreter reads `previous_aL` after assigning y, probably an upstream slip; Azahar's decompiler leaves aL as the inner loop left it; neither verified on hardware). DST, DSTI and LIT, which Azahar's decompiler, interpreter and JIT do not implement, are translated as vs_3_0 defines them and flagged `uses_unverified_instructions`: the oracle's version was written from the same definition, so nothing independent confirms them (nihstro's table calls opcode 0x07 `lit`, "Clamp for lighting", and 3dbrew LITP: the semantics may differ). Temporaries and outputs start at (0, 0, 0, 1) (Azahar's generator; the interpreter keeps old values), so a program that reads an uninitialised temporary agrees with the oracle by construction. A program whose reachable code, jump, call or entry leaves the loaded words, never ends, recurses, calls in a cycle or has an unknown opcode is rejected with a message (a category and a word offset, never the word); JMPC and JMPU dispatch is bounded to 65,536 iterations (a note on the result); EMIT and SETEMIT do nothing, as in Azahar's decompiler.
  - **The PICA float rules** are always on (MUL, DP3, DP4, DPH, MAD and the first product of DST: 0 times infinity is +0, a NaN factor stays NaN; MAX and MIN as the hardware), written with bit-level NaN tests and bit-level selection so that a driver cannot fold them; lavapipe and the interpreter did not differ. The RX 6700 XT's driver is the PC's leg: the dump check below runs on whatever device the backend chooses. **RCP and RSQ are rounded as the interpreter computes them** (`1.0f / x` and `1.0f / sqrtf(x)`, each step to nearest) *(2026-10-25, the dump check on the RX 6700 XT)*: the first PC dump check (G1 to G4: 5,989 draws, 66 programs, 91,683 vertices) met 6 mismatches, all in one program (3 vertices of one draw, two lanes of one output) whose normalization (dp3, rsq, mul) is followed by 1 + z with z near -1 and a second rsq; the RX 6700 XT's `inversesqrt` and `1.0 / x` are within an ulp of the true value but not always the rounded one (about one input in nine differs from the CPU's), and the cancellation turns 1 ulp into 2.7e-5, above the 2^-16 of the comparison. The first version of that (a float residual with `fma` around the device's value, four ±1-ulp steps) passed on the RX 6700 XT and failed in CI on lavapipe (*2026-10-30*: 3018 of 32768 results differed in `RCP and RSQ round as the interpreter does`, 1617 of them rsq, and 480 of 16384 values in the normalization case), because it assumed a fused `fma` and a start value within 4 ulp, which Vulkan does not promise. The translation now computes the rounded value **in exact integer arithmetic** (`pica_magnitude`, `pica_rcp_residual`, `pica_rcp_significand`, `pica_rcp_normal`, `pica_sqrt_residual`, `pica_sqrt_significand`, `pica_rcp`, `pica_rsq` in the prelude of `glsl_decompiler.cpp`; the proofs are in the comment above them) and uses no `fma` and no float operation that must be exact. RCP: with `s = m * 2^(e-23)` the float nearest to `1/s` is `Q * 2^(-24-e)` with `Q` the integer nearest to `2^47 / m` (never a tie, since `2^48 / m` is never an odd integer), and `Q` is that integer iff `2 |2^47 - Q*m| < m`, decided on the 64-bit product of `umulExtended` and a subtraction with borrow. RSQ is `1.0f / sqrtf(x)`: the root `C` is the integer nearest to `sqrt(N)` (`N = m * 2^23` or `m * 2^24` by the parity of `e`) iff `-C < N - C*C <= C` (the same test as `(2C-1)^2 < 4N < (2C+1)^2`, no ties), then the reciprocal of `C * 2^((e>>1)-23)` as above, and the result is assembled from its bits. The start values are float estimates (`2^47 / m`, the device's `sqrt` of an exact float) that two jumps `Q += round(d/m)` (RCP) or three Newton steps `C += round(R/2C)` (RSQ) bring to within 1 of the answer whatever the device's rounding is (RCP from any start in `[2^23, 2^24]`; RSQ from a start within 2^-4 of the root), followed by three exact `±1` steps (at most one is used when the estimates are the exact ones; two with the deliberately bad ones of the test). The range is every normal operand whose result is normal (RCP biased exponent 1 to 252, RSQ positive 1 to 254), tested on the bits; outside it (zero, denormals, infinity, NaN, a negative RSQ operand) the plain device operation, whose result the interpreter shares. EX2 and LG2 stay the device's: no captured program needed them. The oracle is the interpreter port, as the spec says; that Azahar's JIT or the hardware gives the same bits is not claimed: if the reference runner's vertex path rounds RCP and RSQ differently, N2-20's images would show it. With the first version the dump check on the same four captures printed mismatches 0; it has to be repeated with the integer version (pending, game data). Checked without game data: the integer algorithm mirrored line by line on the CPU (`rcp_mirror` in `gpu_shader_test.cpp`, with start values and estimates deliberately moved to show they do not matter) equals `1.0f / x` and `1.0f / sqrtf(x)` for every power of two, the extreme significands and 200000 random values; a device case feeds the near-ties of both roundings and the neighbours of the powers of two; and a throw-away exhaustive run (every one of the 2^23 significands at the exponent fields 1, 127, 128, 252 and 254, on the CPU mirror and on the RX 6700 XT) found 0 differences in 41,943,040 operand values (both operations except RCP at field 254). 48 cases of `gpu_shader_test` pass on the RX 6700 XT. What only CI on lavapipe confirms is that the device's float estimates there stay within the margins above (they are wide) and that `umulExtended` and `usubBorrow` compile as expected. The eight prelude helpers are emitted into every shader (glslang's time for 17 instructions did not change measurably: 5 to 8 ms per program on the RX 6700 XT PC before and after, run to run noise included).
  - **Where the interpreter and the structured readings disagree** (the oracle is the interpreter, as the spec says; the translation follows the structure, like Azahar's decompiler and x64 JIT; `gpu_shader_test.cpp` pins both sides; `TranslatedVertexShader::differs_from_interpreter` is a hint: it flags the shapes known to differ, and with an over-approximation it may flag a program on which the two agree). The interpreter tests one scope end per instruction (the call stack, then the if stack, which pops one entry and overwrites the program counter, then the loop stack, all against `old_program_counter + 1`), so a jump over an else branch or over the rest of a scope lands where the next test does not fire: (1) a loop or call body that ends with an if/else: after the then-branch the loop does not iterate again; (2) a loop or call body that ends with an if without else: when the condition is false the loop does not iterate and the call does not return; (3) an if, with or without else, at the tail of the then-branch of an if that has an else: the outer else branch runs as well; (4) two loops that end on the same instruction: the outer one does not iterate; (5) a call or jump that is the last instruction of an if, call or loop scope is never taken. Not flagged and equal: an if or if/else in the middle of a body, an if/else at the tail of an outer else-branch, nested loops whose inner loop is not last. **Known gap of the hint** (reviewer's nits): a LOOP whose end is the else address of an if that has an else, or the end of an enclosing call, also differs and is not flagged. Which reading the hardware follows is not known. A mismatch in a flagged program is first read as the interpreter's quirk (the dump check says so and counts such programs); a mismatch in an unflagged program is a translator bug until shown otherwise, except for the two shapes of the gap.
  - **The geometry-shader clause of the Goal is not delivered.** Azahar's decompiler does not translate geometry programs (EMIT and SETEMIT log an error), `rhi-spike.md` 5.4 says geometry-shader draws are CPU draws, and `gpu-fragment-design.md` 8 (k) records that no package builds that CPU path (a CPU shader runner for the vertex and geometry shaders, primitive assembly with the quaternion fix-up, a streamed vertex batch: 38.99 to 98.30 percent of the draws) and that the planner must decide which of the two is true. The vertex program of a geometry-shader draw is an ordinary vertex program and is translated and tested like any other. `needs-decision` for the planner and the maintainer.
  - **The dump check, for the PC** (the last *Done when* line; the row stays `dump-check pending`): `MH4N_REQUIRE_VULKAN=1 MH4N_SHADER_CAPTURES=<.mgpu files or directories, separated by ':' (';' on Windows)> ctest --test-dir build/native -R gpu_shader -V`. Each capture is replayed once through the capture player and the PICA processor; at every draw the draw's vertex program is translated (through the cache), run on the device for the draw's own uniforms and its first 64 vertices as N2-05's `VertexLoader` loads them (a compact stream, outputs to a storage buffer) and compared with the interpreter port. A pass is exit 0 with `shader dump check: N captures; draws seen D, distinct programs P, programs checked P, vertices compared V, mismatches 0, translation failures 0` (P counts the programs of every draw whatever its load status; the two P are equal and above 0, and V is above 0), followed by `shader dump check: program runs R, draws without vertices S, loader errors 0, programs with DST/DSTI/LIT U, programs with an interpreter-differing shape K (draws with mismatches in them 0), device refused a pipeline 0, oracle problems 0`. It prints counts only, never a value or an instruction word of the game. U above 0 means a captured program uses an instruction Azahar does not implement: read it before trusting that program's pass. K above 0 with 0 mismatches is a pass (the shape is there and the two readings agreed on those inputs). A draw without vertices is fine only if another draw runs its program; a loader error cannot happen in a replayed capture and fails the check. A run that does not pass adds `shader dump check: NOT PASSED: <counts and the first problem>; hint: differs_from_interpreter is a hint: ...` (the hint reads the mismatch as the interpreter's quirk in a flagged program and as a translator bug in any other). Without the variable the case skips with a message.
  - **For N2-08 and N2-16.** A vertex-only pipeline in a pass with no attachments works on the frozen interface as the spec says, and Storage usage works in the Readback heap, so a shader can write where the host reads; a Device-heap storage buffer read back through `ReadBuffer`'s internal staging copy, or any freed buffer whose memory is reused, shows up as a SYNC-HAZARD under the layer, because the layer does not see the host wait on the timeline: tests that loop over draws keep their buffers alive. `Capabilities` has no float-controls bits (`SignedZeroInfNanPreserve`): a driver that folds NaN in the vertex stage would be a surprise for N2-08. glslang is linked into every binary through `mh4n::all` (about 5 MB each).

The option is exported as the public compile definition `MH4N_RHI_CHECKS=1` or `0` of `mh4n_gpu_backend_core`; N2-27, N2-28, N2-22 and N2b-06 put their checks under the same switch (by linking that module, or by reading the cache variable). ### N2-22 · Renderer thread and synchronisation
- **Size / agent:** M · native-worker-high
- **Depends on:** N2-26, N2-03, N2-04 · **Needs:** dump-check, save
- **Goal:** principles 4 and 6 for the renderer: GX commands are processed on a renderer thread of their own; interrupts are signalled in order; flushes and invalidates are honoured; anything the renderer writes into guest memory happens at the scheduler's safe points.
- **Read first:** [`../ROADMAP.md`](../ROADMAP.md) §3, principles 4 and 6; D56; `native/include/mh4n/gpu.h` (`Host::Post`, `SignalInterrupt`); `docs/research/flat-memory-check.md` (N0-14), if it exists; `docs/research/system-services.md` (the engine's one frame of lag); `docs/research/rhi-spike.md` 6.4, 6.9 (D2, D3) and 9.4 item 5 (the owner rule); `docs/native/rhi.md` (N2-26).
- **Files (allowlist):** `native/src/gpu/queue/**`, `native/tests/gpu_queue_test.cpp`.
- **Spec:**
  - A `Gpu` that wraps another: `Execute`, `WriteReg`, `SetBufferSwap`, `SetColorFill`, `FlushRegion` and `InvalidateRegion` queue work for the renderer thread and return at once.
  - Interrupts go back through `Host::SignalInterrupt` in the order the commands complete.
  - `InvalidateRegion` (the CPU is about to read) waits until earlier commands touching the range are done and written back; `FlushRegion` marks cached data stale before later commands run.
  - Writes into guest memory (fills, transfers, readbacks) are handed to the scheduler with `Host::Post`, except into buffers the request lent (principle 6).
  - At most one frame in flight beyond the one being built (the engine's lag); more blocks the queue, not the game thread, and the counter of such waits is reported (`TakeFrameCounters`).
  - `VBlank(screen)` is queued in order with the commands, so a buffer swap and the VBlank that follows it reach the wrapped GPU in the order the game made them.
  - `ReadReg` is answered at once from a mirror of the registers the wrapper has seen through `WriteReg` (updated when the call is made, not on the renderer thread).
  - Per frame, the renderer thread's busy time and the time the queue spent waiting are reported through `TakeFrameCounters` (the runtime's GPU log reads them, N2b-12).
  - Registered as the GPU wrapper `queue`: the capture player's `--queue` wraps the chosen GPU in it.
  - **The owner rule** (`rhi-spike.md` 9.4 item 5, which constrains D56's threads): the renderer thread owns every image the wrapped GPU makes and is the only thread that records on them; an image reaches another thread (the compositor's, N2b-05) only through a timeline value with its own wait stage (`HandOver` with a `Wait`, or the consumer's `Wait` on the value that produced it, N2-27, N2-28), and never while it is an attachment of an open pass; colour targets are in `GENERAL` at the hand-over because N2-27 sets patch 04's flag on every framebuffer, and depth-stencil targets are never handed over (their attachment layout is `unverified`, N2-27); command lists are recorded and submitted in order per owning thread, not per queue, because the renderer and present threads share one queue behind the backend's submit lock (D56 gives them one device). With `MH4N_RHI_CHECKS` on (N2-26: on by default in every build type, `RelWithDebInfo` included), the wrapper asserts that every call it forwards to the wrapped GPU runs on its renderer thread, calling the backend's owner-rule handler otherwise, and `gpu_queue_test` has a case where a forwarded call from another thread calls a test handler; the backend's own checks (N2-26 to N2-28) catch the rest.
- **Done when:**
  - ctest passes: command order and interrupt order under a fake host; an invalidate that waits for an earlier transfer; writes arriving only through `Post`;
  - (with the dump) the capture player in `--chained` mode gives the same results with `--queue` as without it on the G1–G4 captures.
- **Traps:** -
- **As built (N2-22), for N2-08, N2-23, N2b-12 and N2b-18** (the module is `native/src/gpu/queue/`, `mh4n_gpu_queue`, `DEPENDS mh4n_gpu_backend_core`; the API and the meaning of every call are the header comment of `queue_gpu.h`; it uses no Vulkan type and nothing in `native/include/mh4n` changed):
  - **Two ways to get it.** `QueueGpu(host, make_inner)` is the asynchronous wrapper: the wrapped GPU is made on the renderer thread, with a `QueueHost` as its `Host`. The registry's `queue` wrapper (the capture player's `--queue`) is **lockstep** (each call returns when the renderer thread has done it), ignores the `Host` it is given and wraps a GPU built on the player's thread with the plain host: the player judges memory, interrupts and registers after each call and may not be edited, so an asynchronous wrapper would race its judgement. N2b-12 builds `QueueGpu` directly.
  - **The frame limit is a reading of the spec by the orchestrator, for the maintainer to overrule.** A frame ends at `VBlank(0)`. The first version blocked the caller of `VBlank(0)`, which is the scheduler thread and the only producer, so a slow renderer would have stalled every guest thread, the audio and the timers (principle 4, and the spec's "blocks the queue, not the game thread"). Now `max_frames_in_flight` (default 1, the engine's lag) is a counting threshold, not an invariant: a `VBlank(0)` that finds that many frames queued or in flight is counted in `queue_frame_waits` and its caller is not blocked, since the engine's own wait (the guest thread waits alone for the completion interrupts, which come in completion order) bounds the queue. `max_frames_queued` (default 4, at least lag + 1) is a safety cap on memory: a `VBlank(0)` that finds that many frames queued blocks until the renderer finishes one, so in a runaway case it can block the game thread. `queue_wait_us` is the callers' blocked time (the cap, `InvalidateRegion`, an unseen `ReadReg`, lockstep calls), not the renderer's idle time; `translate_us` is the renderer's busy time. Both are reported through `TakeFrameCounters`.
  - **`InvalidateRegion`** waits for every earlier command (the wrapper cannot decode ranges, so this is a correct superset of "touching the range") and then runs, on the calling thread, the writes the wrapped GPU handed to `Host::Post` through `QueueHost` up to that point, each once; a wrapped GPU built with the plain host gets the wait, but its writes land at the host's next safe point. `QueueHost` forwards `SignalInterrupt` straight to the real host while the posted writes run inside `InvalidateRegion`, so a write of command N+1 can land before the interrupt of command N is delivered (a command's own write is still before its own interrupt). A wrapped GPU must never wait for the scheduler: waiting for the completion of its own `Post` while the scheduler is blocked in `InvalidateRegion`, the cap or a lockstep call would deadlock.
  - **`ReadReg`** answers from the mirror for a register written through the wrapper (cleared by `LoadInitState`), even if the GPU later changes it itself; a register never written is read from the wrapped GPU after the queue and waits on every such call (it is not cached, since the GPU may change it).
  - **The owner rule** (`rhi-spike.md` 9.4 item 5): every forward to the wrapped GPU goes through `QueueGpu::ForwardTarget`, which calls `rhi::ReportOwnerRuleBreach(OwnerRule::WrongThread, ...)` off the renderer thread when `MH4N_RHI_CHECKS` is on; `QueueHost::GuestPointer` reports the same breach and returns `nullptr`, because it is scheduler-thread only (principle 6). A wrapped GPU that writes FCRAM or VRAM itself (`cpu-gx`'s fills, transfers and DMA) would do it on the renderer thread under the asynchronous queue: it must `Host::Post` those writes; `gpu_null`'s DMA of heap pages uses `GuestPointer`. The wrapped GPU is destroyed on the renderer thread, and queued work is drained first.
  - **Exceptions on the renderer thread** are logged and the queue goes on (the call counts as completed, the frame of a `VBlank(0)` that threw is released); calls that wait for an answer (the debug calls, an unseen `ReadReg`) rethrow to their caller. Fatal under `MH4N_RHI_CHECKS` (as the owner-rule handler is) would also be defensible for an owner of GPU images; the maintainer may choose.
  - **Tests:** `gpu_queue_test`, 28 cases, with a fake host and a fake wrapped GPU and a synthetic `MGPU` scene: order and thread, interrupt order, the invalidate's wait and its write-back, writes only through `Post`, the counting and the cap, the mirror, exceptions, destruction, the owner rule with real threads, a 3000-operation mixed run, the capture player with and without `--queue`. Every case runs under a 30 s watchdog (a hang is a failure within seconds). The claim that each posted write runs once is caught only under ThreadSanitizer (`native-tsan` runs this binary). The (with the dump) item is the procedure in `docs/native/capture-player.md`, *Running behind the `queue` wrapper*.
  - **For N2b-12, N2b-18, N2-08 and N2-23:** see the Traps added to N2b-12, N2-08 and N2-23 on 2026-10-24 (build `QueueGpu` directly; create GPU images on the thread that calls `Execute`; DMA and GX writes must not run on the renderer thread).
- **Out of scope:** the game runtime's use of it (N2b).

### N2-16 · Pipeline cache, ubershader and background compilation
- **Size / agent:** L · native-worker-high
- **Depends on:** N2-07, N2-20, N2-15 · **Needs:** dump-check, save, pc
- **Goal:** no visible stutter from shaders (principle 5): pipelines are compiled ahead of time from a list kept on the player's PC, cached on disk, and while a missing one compiles in the background, the ubershader draws.
- **Read first:** `docs/native/gpu-fragment-design.md` (4.3, 4.5, 4.6, 8 (e) and (f)); D5 (with the outcome of N2-35, and of N2-39 if it has reported), `docs/research/spike-1b.md` (N2-35) and `docs/research/ubershader-timing.md` (N2-39), if it exists; `docs/research/pica-census-keys.md` (N0-40), if it exists; N2-33's `pipeline_key.h` and N2-36's and N2-37's *As built*; `docs/native/rhi.md` (N2-28's pipeline cache); `docs/research/rhi-spike.md` 5.8, 6.1 (G10, X8), 6.9 (E) and 9.3; in Azahar: `src/video_core/renderer_vulkan/vk_pipeline_cache.cpp` and `vk_shader_disk_cache.cpp`; RT64's ubershader and pipeline-list approach.
- **Files (allowlist):** `native/src/gpu/pipeline/**`, `native/src/gpu/{native,fragment}/**` (the draw path through the pipeline cache), `native/tests/gpu_pipeline_test.cpp`.
- **Spec:**
  - The pipeline key from the design (N2-33's `PipelineKey`, serialised as `core::ToPlume` consumes it plus the topology, the vertex layout and the stage ids); a disk cache in the user folder, with the driver's `VkPipelineCache` data and our list of keys (with the struct hash of the key types in its header, as Azahar's `FILE_INFO`); precompiling the list at start-up on worker threads, the fallback pipelines first, then the specialised ones by decreasing use count. This WP's provider implements N2-33's `PipelineProvider` and is registered through `mh4n/registry.h`, so `--gpu native` takes it instead of the default one.
  - **The driver's part** is the backend's blob API (N2-28: `SavePipelineCache`, `LoadPipelineCache`, which refuses a blob from another vendor, device or `pipelineCacheUUID`); this WP owns the files and the key list, and creates pipelines on its worker threads (the backend allows creation from several threads, N2-28). **No graphics pipeline library:** neither M2 driver has one (9.3) and the vendored plume uses none on any device, so the ubershader and the cache are the only means against stutter; the key includes the blend state on every device (X8).
  - On a miss: draw with the ubershader at once, compile the specialised pipeline in the background, switch when it is ready. Azahar skips a draw whose pipeline is not ready when its asynchronous compilation is on (off by default, 5.8); here such a draw is never skipped: it goes through the fallback pipeline. *(D5 pass, design 4.5 and 8 (e))* **The fallback pipeline** uses the trivial vertex stage with the draw's vertices shaded on the CPU by N2-36 and N2-37 (the design's fallback (ii)), so the fallback pipelines are bounded by the fixed-function state, the attachments and the pass kind, with no fix-up stage and no translated vertex shader. Plume bakes the fixed-function state, so **a fallback that does not exist yet** (a never-seen fixed-function state, attachment format or pass kind) is itself a compile: it is built synchronously on the render thread once, counted (`pipeline_sync_builds`) and listed, so it never repeats on that machine. Under option 1 a specialised pipeline is generated and compiled with N2-06's glslang on a worker; *(Option 1b, not taken: the spike failed T2 on 2026-10-30, so the workers generate and compile.)* N2-39 runs beside this WP (both after N2-15) and does not hold it back: if, when this WP starts, D5's row already says on N2-39's verdict that the ubershader alone fits the budget, the compile-and-switch part is not built (the list, the disk cache and the counted fallback builds still are); otherwise it is built, and a later verdict that the ubershader fits changes only the default (`--force-ubershader` on), which is the orchestrator's decision, not a rework of this WP.
  - Keys seen while playing are appended to the list, so the next start compiles them.
  - **In the capture player** (options and counters registered here): `--no-ubershader`, `--warm`; `--force-ubershader` is N2-08's option (the design's `--ubershader-only`), kept under that one name and honoured by this WP's provider with N2-33's meaning: the ubershader for the fragment stage with the draw's own vertex stage and fix-up stage (so it measures the fragment cost the same before and after this WP), while a miss's fallback is the trivial vertex stage with CPU-shaded vertices described above; per frame, how many draws used the ubershader, `pipeline_sync_builds`, the GPU time (N2-28's `FrameGpuTimeNs`, already in the report through N2-08), and the frame time with a cold and a warm cache.
- **Done when:**
  - ctest passes: the key's stability, the disk cache's round trip, the ubershader fallback (forced misses give the same image within the thresholds);
  - (with the dump) G3's capture with a cold cache blocks on a compilation only for the counted synchronous builds (`pipeline_sync_builds`: one per new fixed-function state, attachment format or pass kind, none for a vertex program or a fragment key), and passes the thresholds with and without the ubershader;
  - (the maintainer) on the reference PC, with a warm cache, no frame of G3's capture takes over 8.3 ms because of a pipeline.
- **Traps:** -
- **Out of scope:** pipelines for the app's own UI (N2b).
