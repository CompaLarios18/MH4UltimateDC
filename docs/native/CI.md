# Native CI

The workflow is `.github/workflows/native.yml` ("Native CI"). It never uses game data: the runner is built and started without a game, and the tests use synthetic data. The existing `ci.yml` (pytest and the game-data guard on every PR) stays as it is.

## Triggers

| Trigger | What runs |
|---|---|
| `push` to `native` or to a `wp/**` branch | `tools`; `native`, `native-windows`, `native-macos`; `changes`, then `runner` if it says so |
| `pull_request` into `native` | `native`, `native-windows`, `native-macos`; `changes`, then `runner` if it says so (the Python tests are `ci.yml`'s job on PRs) |
| `workflow_dispatch` | `tools`, `native`, `native-windows`, `native-macos`, and `runner` always |

A newer push to a `wp/` branch (or to a PR) cancels the older run of the same ref; runs on `native` are never cancelled.

## Jobs

- **`tools`** (pushes and dispatch): the steps of `ci.yml`: Python 3.12, `clang lld llvm`, `pip install -r requirements.txt`, `python -m pytest -q`, and the guard that fails if `git ls-files` lists game data.
- **`native`** (N1-01; on every trigger, `ubuntu-24.04`): installs `clang lld llvm cmake ninja-build libvulkan-dev mesa-vulkan-drivers glslang-tools spirv-tools` and `pip install -r requirements.txt` (the ARM test programs are built with `tools/difftest.py`), then configures `native/` with the one configure line of `wp/N1.md`, builds, runs `ctest`, runs `python3 tools/native/check_native_deps.py` (nothing under `native/` may use Azahar), and runs `tests/test_conformance.py` with `MH4N_RUNNER` set to the native runner it just built (the ARM conformance programs on `mh4u_native_runner`, except those listed in `NATIVE_NOT_YET`; `docs/native/runner.md`). The step "Vulkan probe on lavapipe" (N2-24) runs `build/native/bin/mh4n_vkprobe` (`mesa-vulkan-drivers` makes lavapipe a device), prints its table, fails unless the table has a `device:` line naming `llvmpipe`, and checks that the probe's own `--json` read back by `--from-json` gives the same table (`docs/research/vkprobe.md`).
- **`native-windows`** (N1-22; `windows-latest`, steps run in bash): Python 3.12 and `pip install -r requirements.txt`; llvm-mingw, fetched by `build_game.fetch_compiler` (the archive `LLVM_MINGW_URL` names in `tools/build_game.py`) into the absolute folder `build/toolchain` (its progress output goes to stderr, the step reads only the folder of the compiler it returns, checks that the compiler is there) and puts that folder on `PATH` (the runner needs its `libc++.dll` and `libunwind.dll` at run time); Ninja from the image (Chocolatey if missing). Configure is the one configure line with `x86_64-w64-mingw32-clang` and `-clang++`. Then build (`cmake --build build/native -- -k 0`: ninja keeps going, so one run lists every error; every step from the tests to "The packaged tools start" has `if: ${{ !cancelled() }}`, so a failing `ctest` does not hide the conformance result, and the job still ends red; the step "The packaged tools start" is the last of them, the artifact upload keeps the implicit `success()` and runs only when all of them passed, and not on pull requests; the artifact `mh4n-runner-windows` carries llvm-mingw's runtime DLLs (Apache-2.0 with LLVM exceptions) without their licence texts: it is for the maintainer's measurements, and the packaging of N3 must ship the notices), `ctest` with `MH4N_REQUIRE_TEST_DATA=1` (there are no Vulkan-device tests yet; the N2 tests will skip without a device), `tests/test_conformance.py` with `MH4N_RUNNER` set to `mh4u_native_runner.exe`, and `check_native_deps.py`. The test program of `cpu_test` and the code libraries of the conformance programs are PE DLLs built with the same llvm-mingw; `native/src/cpu/CMakeLists.txt` keeps the `.so` file names that `cpu_test.cpp` and `tests/test_conformance.py` use (`LoadLibraryExW` takes any file name), and the conformance step sets `CCC_OVERRIDE_OPTIONS=^--target=x86_64-w64-mingw32` so the test's plain `clang` builds for Windows. Windows notes for code in `native/`: a file that includes `<windows.h>` defines `WIN32_LEAN_AND_MEAN` and `NOMINMAX` first, and a file that includes `<windows.h>` and `cpu.h` does `#undef Yield` right after the include (winbase.h defines `Yield()` as an empty macro, which turned `GuestThread::Yield` into `void ;`); other `windows.h` names we use are avoided instead (`NewEvent`, not `CreateEvent`). The Python tools that run the LLVM programs (`port/tests/build_svc_test.py`) resolve them with `shutil.which` (`difftest.tool`) and run the full path: on Windows `CreateProcess` appends `.exe` only to a name without an extension, so a bare `ld.lld` is not found although `ld.lld.exe` is on `PATH`. `native/CMakeLists.txt` sets `CMAKE_LINK_LIBRARY_USING_WHOLE_ARCHIVE` to plain `--whole-archive`/`--no-whole-archive` for MinGW, because CMake probes `CMAKE_LINKER` (not lld) and lld's MinGW driver has no `--push-state`. The same llvm-mingw release has a Linux-hosted build, so the errors of this job can be found without CI: `cmake -S native -B build/native-win -G Ninja -DCMAKE_SYSTEM_NAME=Windows -DCMAKE_C_COMPILER=<root>/bin/x86_64-w64-mingw32-clang -DCMAKE_CXX_COMPILER=<root>/bin/x86_64-w64-mingw32-clang++ -DMH4N_WERROR=ON` with `<root>/bin` on `PATH` (that cross build compiles, links and builds the PE test libraries; the binaries do not run on Linux by themselves, but with `wine` installed and `WINEPATH` set to llvm-mingw's `bin` and `x86_64-w64-mingw32/bin` every cross-built test binary passed under wine 9.0, which is a close approximation of the Windows job but not a replacement for it).
  - **Artifact `mh4n-runner-windows`** (pushes and dispatch, not pull requests; 30 days): `mh4u_native_runner.exe`, `mh4n_ipc_replay.exe` (the IPC replay), `mh4n_capture_player.exe` (the capture player) and `mh4n_vkprobe.exe` (the Vulkan probe, N2-24; it loads `vulkan-1.dll` at run time, so no Vulkan file is in the artifact), and the llvm-mingw DLLs they import, directly or through another DLL (found with `llvm-objdump -p` over the four programs, looked up in llvm-mingw's `bin/` and in `x86_64-w64-mingw32/bin/`; each DLL once), all in one folder, so the four command-line tools run on any Windows PC without a build. No game data is in it (they are our binaries); the three diagnostic tools are stripped of debug information (`RelWithDebInfo` keeps about 35 MB of DWARF inside each MinGW executable), the runner is packaged as it was, and the step lists the files and the folder's size. The step "The packaged tools start" runs each of the four with a `PATH` that has only the Windows folders and checks that `--help` prints its usage (`usage: mh4u_native_runner`, `usage: mh4n_ipc_replay`, `usage: mh4n_capture_player`, `usage: mh4n_vkprobe`) and exits 0, for all four in one run, and fails naming each tool that did not. `mh4n_hdpack` is not in it. Fetch it like the Linux runner's, with the artifact name `mh4n-runner-windows` (`gh run download <run> -n mh4n-runner-windows`).
- **`native-macos`** (N1-22; `macos-26`, the label `macos.yml` uses; arm64): Xcode's `clang` and `clang++` build `native/` (one configure line); `brew install ninja llvm lld` supplies the LLVM tools the ARM test programs and code libraries call (`ld.lld`, `llvm-objcopy`, `llvm-readelf`, `llvm-nm`). `$GITHUB_PATH` prepends, so Homebrew's whole `llvm/bin` is not put on it (its `clang` and newer libc++ would win over Xcode's, and the vendored {fmt}, which must stay as upstream, does not compile against that libc++: it uses `malloc`/`free` without `<cstdlib>`); the step puts symlinks to just those four tools in `$RUNNER_TEMP/llvm-tools` and adds that folder. Then build (`-- -k 0` and the same `if: ${{ !cancelled() }}` on the later steps, as on Windows), `ctest` with `MH4N_REQUIRE_TEST_DATA=1`, `tests/test_conformance.py` with `MH4N_RUNNER`, and `check_native_deps.py`. The step "The Vulkan probe starts" (N2-24) prints `file` and `lipo -archs` of `build/native/bin/mh4n_vkprobe`, fails unless it is an arm64-only executable, and checks that `--help` prints `usage: mh4n_vkprobe` (the runner has no Vulkan driver, so the probe is started, not run on a device); the step "Upload the Vulkan probe" publishes that one file as the artifact `mh4n-vkprobe-macos` (30 days; pushes and dispatch, not pull requests; `if-no-files-found: error`). The file is an unsigned arm64 executable with no library beside it (it loads the Vulkan loader or MoltenVK at run time); the zip of an artifact drops the executable bit and a browser download is quarantined, so the maintainer runs `chmod +x mh4n_vkprobe` and, if macOS refuses it, `xattr -d com.apple.quarantine mh4n_vkprobe` (`docs/research/vkprobe.md`). The log prints the page size of the machine (16 KiB on Apple silicon; `native/src/memory` works in host pages, so `memory_test` asserts per-page faults only where the host page is 4 KiB and, on a coarser host, what the module guarantees there: a freed guest page inside a mapped host page stays accessible and reads zero, and only a whole released host page faults).
- **`changes`**: decides whether `runner` is needed, from the files changed under `port/`, `tools/`, `config/` and `.github/workflows/native.yml`:
  - dispatch: always;
  - PR: the files of the PR (`base...head`);
  - push to `wp/**`: the files changed since the merge base with `origin/native`;
  - push to `native`: the files of the pushed commits (`before..HEAD`); a new branch or a force push, where `before` is unusable, builds.
- **`runner`**: the reference runner, in the container image `linux.yml` uses (`opensauce04/azahar-build-environment:latest`).
  1. Azahar is cloned and checked out at `port/azahar/COMMIT`, submodules fetched, `port/azahar/azahar.patch` applied.
  2. ccache through `actions/cache`, keyed on the hash of `COMMIT` and the patch (plus the commit sha; the restore key is the hash alone).
  3. Configure with the flags of `port/README.md`'s Linux runner build (no Qt, no Vulkan or OpenGL, no SDL2, software renderer), build target `mh4u_runner`.
  4. Package `mh4u_runner`, every shared library `ldd` resolves except the C library's own, and `run.sh` (sets `LD_LIBRARY_PATH` to the bundled `lib/`) into `mh4u-runner-linux.tar.gz`; a step unpacks it and checks `run.sh --help` prints `usage: mh4u_runner`.
  5. Upload as artifact `mh4u-runner-linux`, kept 30 days.

## Fetching the runner (cloud session)

The newest runner that still has its artifact, for a branch (`<branch>` is `native` or a `wp/...` name). From a cloud session this needs the environment to allow the host GitHub serves artifacts from, `*.blob.core.windows.net` (the download fails with `Forbidden` otherwise; see `AGENTS.md` §7):

```bash
id=$(gh api 'repos/CompaLarios18/MH4UltimateDC/actions/artifacts?name=mh4u-runner-linux&per_page=50' \
  --jq '[.artifacts[] | select(.expired | not) | select(.workflow_run.head_repository_id == .workflow_run.repository_id) | select(.workflow_run.head_branch == "<branch>")][0] | .workflow_run.id')
case "$id" in ""|null) echo "no runner artifact for <branch>"; exit 1 ;; esac
mkdir -p build/runner
gh run download "$id" -n mh4u-runner-linux -D build/runner
tar -xzf build/runner/mh4u-runner-linux.tar.gz -C build/runner
build/runner/run.sh --help        # prints the runner's usage
```

Only pushes (to `native` and `wp/**`) and dispatches publish the artifact, never pull requests, and the recipe also requires the run to come from this repository (a fork's branch can carry any name). A push that changed none of the watched paths builds no runner, so the newest artifact of a branch may come from an earlier push: compare the run's `head_sha` (`gh run view <id> --json headSha`) with `git rev-parse <branch>` when it matters, and for a branch without a runner use `native`'s, or dispatch one (`gh workflow run native.yml --ref <branch>`).

## Building it when there is none

```bash
gh workflow run native.yml --ref native
gh run list --workflow native.yml --branch native --limit 1     # then: gh run watch <id>
```

GitHub accepts a dispatch for a workflow that is not on the default branch once it has run at least once. Dispatch always builds the runner. Artifacts expire after 30 days, so a quiet branch needs this now and then.

## Not covered

The port's Windows and macOS builds of Azahar (`windows.yml`, `macos.yml` on `main`; dispatch them with `ref` set to any branch); the native runner's own are `native-windows` and `native-macos` above. The game-data guard of N0-19 is its own workflow, `native-guard.yml`: it runs `tools/native/check_no_game_data.py --range` over the pushed or proposed commits, on the same triggers (pushes to `native` and `wp/**`, PRs into `native`). On a PR it runs the script of the base branch (`git show <base>:tools/native/check_no_game_data.py`), so a PR cannot weaken the check that judges it; until the base has the script (the PR that introduces it), it uses the PR's own. The allowlist `config/native/large_files.txt` is still the PR's: each entry needs a path and a SHA-256 and is reviewed. A PR can still change the workflow files themselves, so review changes to `.github/workflows/` like code that guards the repository. Both workflows set `persist-credentials: false` on every checkout, so the read-only token is not left in `.git/config` while PR-controlled scripts run.
