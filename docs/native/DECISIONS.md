# Decisions (native port)

The decision log for branch `native`. **Decided** entries were settled by the maintainer and change only if he says so. **Recommended** entries are the plan's default: work packages build on them, and a work package that finds a reason to change one stops and reports `needs-decision` instead of improvising. **Open** entries name the work package that settles them.

Only the orchestrator edits this file. To add or change an entry, add a row (or edit the status) in a batch PR, with the evidence linked, and say so in the PR description.

| ID | Topic | Decision | Status | Settled by / notes |
|---|---|---|---|---|
| D1 | Thread model | Fibers (reuse `port/src/fiber.cpp`) with our own scheduler, strict priority per virtual core. N1 drives all virtual cores from one host thread (as Azahar does); N6 gives each virtual core its own host thread. Host threads never run game code | Recommended | Confirm with the kernel census (N0-12). Fallback: one host thread per guest thread with a run token (N64Recomp's ultramodern model) |
| D2 | Where the OS is replaced | At the SVC and IPC level (the SDK's code stays as recompiled); SDK-function overrides only for hot paths, later | Recommended | Confirm with the IPC traces (N0-21) and the first boot (N1-21) |
| D3 | Renderer level | PICA command lists (works however the commands were built: DMPGL, saved command lists, hand-written writes); the DMPGL API level only if profiling asks; engine level in N6, piece by piece | Recommended | — |
| D4 | RHI and backends | SDL_GPU is ruled out (3.4.18 has no storage writes in fragment shaders, no logic ops, no triangle fans, no geometry shaders). Candidates: plume (MIT; Vulkan, D3D12, Metal; no interlock, raster order groups or framebuffer fetch exposed; unstable API), plume extended, or a thin RHI of our own. Vulkan first; Metal under the rule of `docs/research/metal.md`; D3D12 only if needed | **Open** | The spike N2-01, run on the RX 6700 XT (interlock on AMD: RADV since Mesa 23.2, AMDVLK since 2024.Q4.1; the spike checks the Windows driver) and the M2 |
| D5 | Fragment pipeline | Our own fragment-pipeline generator, designed for precompiled pipelines plus an ubershader, with one module per feature (sampling, lighting, fog and gas, procedural textures, shadows) | **Open** | N2-07 writes the design; the maintainer decides |
| D6 | Licence and Azahar code | GPL-3.0-or-later. Individual pieces of Azahar may be copied (texture decoders, shader translation, DSP algorithms, the room protocol), each with a header naming the source file and Azahar commit, and listed in `native/THIRD_PARTY.md`. No Azahar module is linked and none of its architecture (kernel, memory system, clock, patch) is reused. Azahar's master moved from GPLv2+ to GPLv3+ on 2026-10-03; both are compatible | **Decided** (2026-10-15) | Maintainer |
| D7 | Rooms | Compatible with Azahar's room protocol (ENet, `network_version` 4), client and server | Recommended | N4 |
| D8 | SDL for the native executable | SDL3 (3.4.18 or later) | Recommended | N0-02 builds it in the cloud |
| D9 | RomFS on disk | Extracted once at setup into a game folder (`tools/native/prepare_game.py`, on top of `tools/extract_ncch.py`) and served as the RomFS image the SDK expects; LayeredFS on top | Recommended | N1-03, N1-12; LayeredFS in N3 |
| D10 | Console model | Old 3DS: the mode the HD texture pack is made for (its author notes the monsters' HD textures show only without New 3DS mode). The C-stick comes through `ir:USER` (Circle Pad Pro). The `new_3ds` setting goes away in the native port | **Decided** (2026-10-15) | Maintainer |
| D11 | The Azahar build after 1.0 | Development reference (oracle), out of the release packages | Recommended | — |
| D12 | Transition | Two executables (Azahar-based with SDL2, native with SDL3) sharing the UI through `IRuntime`; the launcher picks one | Recommended | N0-20 and N0-24 build the seam |
| D13 | Code that wasn't recompiled | A minimal interpreter of our own, generated from the recompiler's own instruction semantics, that logs each entry it runs for the next recompilation. A code library that doesn't match the loaded code is refused, and the launcher offers to rebuild | **Decided** (2026-10-17) | Settled by the orchestrator at the maintainer's request. N1-24 showed the generator approach feasible (20 of 20 spike forms match the recompiled code) and N1-28 built it: `tools/recomp/interp_gen.py`, `native/src/cpu/interp/` |
| D14 | HD textures | On by default, but never in our packages: the setup step comes preselected, downloads from the author's own links (the catalog's code), pre-processes the pack on the player's PC (BC7 with mipmaps, indexed by hash) and turns custom textures on. Players can untick it | **Decided** (2026-10-15) | Maintainer |
| D15 | Frame-rate target | v1.0: 120 fps stable on the reference PC (Ryzen 5 5600X + RX 6700 XT) at 3440×1440 (to confirm) on a 240 Hz monitor, HD pack on. 180 and 240 fps after 1.0 (N6) | **Decided** (2026-10-15) | Maintainer |
| D16 | Branches | All native-port work lives on `native`. Batch branches start from `origin/native`, and work branches from their batch (AGENTS §3). PRs go into `native`, and the maintainer merges them. `main` is merged into `native` after each `main` release; `native` is never merged into `main` before v1.0 | **Decided** (2026-10-15) | Maintainer |
| D17 | Agent models | The main session runs Sonnet 5.5 in ultracode, which the maintainer picks so a session can run many subagents at once. Workers on Sonnet (medium effort; high for the packages marked so), reviewers on Sonnet at high effort. Opus at high effort only for the planner: phase-boundary planning, open-decision analysis, and a package blocked twice for design reasons. Definitions in `.claude/agents/` | **Decided** (2026-10-15) | Maintainer |
| D18 | Toolchain for `native/` | C++20, CMake + Ninja, clang everywhere (llvm-mingw on Windows, as the code library already uses; Apple clang on macOS). Unit tests with doctest, and fmt for formatting, both vendored (MIT), through CTest | Recommended | N1-01 |
| D19 | Frame budget split at 120 fps | Game thread ≤ 4 ms, translation ≤ 3 ms (parallel), GPU ≤ 6 ms at 3440×1440 with the HD pack (parallel) | Recommended | Confirm with the baseline (N0-15) and the measurements of N1-23 and N2-19 |
| D20 | The GPU contract | The runtime and every renderer meet at `mh4n/gpu.h`, which mirrors the entry points of Azahar's `VideoCore::GPU` (GX commands, register writes, buffer swaps, colour fill, cache flushes, interrupts out). GPU captures record exactly those calls, so the null GPU, the capture player and the real renderer are interchangeable | Recommended | N0-05 (the captures), N1-01 (the header) |
| D21 | Numbering like Azahar | Handle values, thread ids, FCRAM allocation order and the main thread's set-up follow Azahar's, so the reference's traces line up with the native ones without normalisation in the common case. The comparators still normalise (N0-04), since interleavings differ | Recommended | N1-02, N1-05, N1-07, N1-27 |
| D22 | Where services run | HLE services run on the calling guest thread's fiber, synchronously, like Azahar's. Work that waits on the host (file reads and writes, later the network) returns a deferred reply; the client thread blocks until the reply is posted back to the scheduler (principle 6) | Recommended | N1-10 |
| D23 | GPU capture format | Our own `MGPU` format (N0-22 defines it, N0-05 records it). Azahar's CiTrace recorder is still in its tree, but at the pinned commit nothing in the GPU code feeds it | Recommended | N0-22, N0-05 |
| D24 | Core 1's time limit | Application threads on core 1 run under the limit APT sets (`SetAppCpuTimeLimit`), alternating as Azahar's `CpuLimiterMulti` does, since the game sets one and runs well on Azahar | Recommended | Confirm with the kernel census (N0-12); N1-27 implements it |
| D25 | When GPU interrupts reach the game | When the GPU signals them, ignoring the delay it passes: Azahar's GSP does that with the reference's settings (`simulate_3ds_gpu_timings` off; MH4U is not on its texture-copy delay list), so the reference's interrupts arrive at once. The null GPU signals each one when its command completes | Recommended | N1-17 |
| D26 | When file replies arrive | By default the native runtime answers file requests no earlier than Azahar's modelled read and open delays, on the game clock, so loads take as many frames as in the reference and golden checks line up (`--io-latency azahar`). `--io-latency none` answers as soon as the data is read; whether players get it is settled in N3's 60/120 fps audit, since faster loads change timings the game may race on | Recommended | N1-12; N3-08 |
| D27 | Vertex shaders | Port Azahar's PICA → GLSL decompiler, with a provenance note (TriAevum did this), and compile its GLSL to SPIR-V with glslang linked as a library; a program is translated when first used and cached by its hash | Recommended | N2-06 |
| D28 | A bad handle inside an IPC command | The native runtime fails `svcSendSyncRequest` with `0xD9001BF7` (Azahar's `ResultInvalidHandleOs`) for a handle that is not in the client's table. Azahar asserts there, so no game has seen either value; `0xD8E007F7` stays for a session handle that is not a client session and leaves no IPC record, which keeps the trace aligners' rule ("the n-th SendSyncRequest that left a record is the n-th IPC record") true | **Decided** (2026-10-17) | Settled by the orchestrator at the maintainer's request. N1-10 (`kResultInvalidHandleInCommand` in `native/include/mh4n/ipc.h`; one constant) |
| D29 | Chat in `IRuntime` | Not until a room UI with chat exists. The app has no chat UI, so the interface grows with its first user (as it dropped `SetPaused` and `SdmcDir`, which had none) | **Decided** (2026-10-17) | Settled by the orchestrator at the maintainer's request. N0-24; N4 adds it with the room UI |
